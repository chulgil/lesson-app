| 항목 | 문서화 상태 | 상세 |

| 학원 모드 개념 | ✅ 완료 | subscription_system_spec.md |
| 학원-선생님 소속 관계 | ✅ 완료 | Membership, 역할 계층(Owner/Manager/Instructor) |

## 3. 누락된 관점/시나리오 식별

### 3.1 학원 관점 누락

1. **학원 웹 관리자 화면 스펙**
   - 학원장/매니저용 웹 대시보드 UI/UX 없음
   - 선생님 관리, 학생 배정, 정산 화면 없음

2. **학원-학부모 직접 소통**
   - 공지사항, 이벤트 전달 채널 미정의
   - 학부모가 학원에 문의하는 플로우 없음

3. **학원 간 학생 이동**
   - 학생이 A학원 → B학원 이동 시 데이터 처리 미정의

### 3.2 선생님 관점 누락

1. **다중 코치 협업 시나리오**
   - 한 학생에게 여러 선생님이 있을 때 커뮤니케이션 방법
   - 과제 중복 배정 방지

2. **대체 선생님 시스템**
   - 선생님 부재 시 대체 레슨 처리
   - 대체 선생님의 레슨 노트/녹음 접근 권한

3. **선생님 평가/리뷰**
   - 학생/학부모의 선생님 평가 시스템
   - 평점 표시, 리뷰 관리

### 3.3 학생 관점 누락

1. **독학 모드 (Unconnected)**
   - 선생님 없이 앱만 사용하는 시나리오 상세 부족
   - 공개 템플릿 활용 플로우

2. **학생 간 소셜 기능**
   - 친구 추가, 연습 랭킹, 그룹 연습
   - (현재는 개인 사용에 집중)

3. **학생 성장 트래킹**
   - 장기 진도 추적 (월별/연별)
   - 레벨 업 시스템

### 3.4 학부모 관점 누락

1. **다자녀 + 다선생님 매트릭스**
   - 자녀별 선생님별 결제 관리 복잡도
   - 통합 대시보드 필요

2. **학부모 커뮤니티**
   - 같은 선생님/학원 학부모 간 소통
   - (현재는 미고려)

## 6. 권장 조치 사항

### 6.1 단기 (즉시)

1. **결제 문서 통합**: payment_flow.md + payment_system.md → payment_unified_spec.md
2. **상태 enum 일원화**: PaymentStatus, InvoiceStatus 정의 통합
3. **invite_system.md(v1) 제거** 또는 deprecated 표시

### 6.2 중기 (Phase 2)

1. **대시보드 스펙 작성**: 학생/선생님 홈 화면 상세
2. **학원 웹 스펙 초안**: 관리자 화면 와이어프레임
3. **다중 코치 협업 가이드**: 시나리오별 처리 방안

### 6.3 장기 (Phase 3+)

1. **독학 모드 상세화**: Unconnected 학생 플로우
2. **학원-학부모 채널**: 공지사항, 문의 시스템
3. **리뷰/평점 시스템**: 선생님 평가

## 7. 결론

### 7.1 전체 평가

| 관점 | 문서화 완성도 | 비고 |
|------|:------------:|------|
| 학원 | 75% | 웹 관리 화면 스펙 부재 |
| 선생님 | 85% | 협업 시나리오 부족 |
| 학생 | 80% | 독학 모드 미흡 |
| 학부모 | 80% | 다자녀 관리 미흡 |

### 7.2 핵심 개선점

1. **결제 문서 통합** - 즉시 필요
2. **대시보드 스펙 추가** - Phase 1.5 전 필요
3. **학원 웹 스펙** - Phase 2 시작 전 필요

### 7.3 강점

- 학생 중심 설계 철학이 일관되게 유지됨
- 3자 데이터 소유권 모델이 명확함
- 양방향 초대 시스템 v2가 잘 정리됨
- 결제 플로우가 상세하게 문서화됨
