# 선생님 E2E UX 감사 계획 (00-plan)

> 작성일: 2026-06-01 (월)
> 범위: 회원가입 → 일정 조절
> 페르소나: 선생님 (음악 레슨 강사)
> 검토 기준: **이탈 방지** (Drop-off Prevention)
> 산출 형식: 리포트 + 전체 스펙 보완
> 벤치마킹: 음악 레슨 전문 + 일반 과외/레슨 SaaS

---

## 1. 배경

선생님 페르소나가 앱에 처음 들어와 첫 학생과 첫 레슨을 완료하기까지의 흐름이 "스무스한지" 확인한다. 누락된 기능·UX 결함·스펙 간 충돌이 있는지 식별하고, 발견된 갭은 기존 스펙을 보완하거나 신규 스펙으로 작성한다.

선생님은 본 앱의 매출·리텐션 핵심 페르소나이며, 학생/학부모는 선생님이 만든 관계 위에서만 동작한다. 따라서 선생님 이탈은 곧 시스템 전체의 누수다.

## 2. 검토 기준 정의

**이탈(drop-off) 방지** — 회원가입에서 첫 수강권 발급, 첫 레슨 진행, 첫 일정 조절까지 각 단계에서 사용자가 포기·장돔·혼선을 일으키는 지점을 식별한다.

| 다른 기준 | 본 검토에서의 위치 |
|---|---|
| 시간 단축 (TTV) | 보조 지표 — 이탈 위험 평가의 한 요소 |
| 신뢰감·프로페셔널 | 보조 지표 — A/B 단계 이탈에 영향 |
| 학습곡선 | 보조 지표 — B/C 단계 이탈에 영향 |

이 기준 하나에 모든 발견 항목이 정렬된다.

## 3. E2E 펀넬 (8단계)

선생님이 거치는 흐름을 8단계로 분해한다. 각 단계는 독립적으로 평가하지만, 단계 간 전이 비용(transition cost)도 함께 측정한다.

| # | 단계 | 시작 상태 | 완료 상태 | 핵심 스펙 |
|---|---|---|---|---|
| A | 유입·로그인 | 익명 | 인증된 user (UserRole.teacher 미확정) | user/user_master.md §2.1 |
| B | 온보딩 v3 Phase A | 인증됨 | 이름·악기·역할 확정 | onboarding/teacher_onboarding_v3_spec.md §3.2 |
| C | 가용시간 설정 | 프로필 최소 완성 | 학생이 예약 가능한 슬롯 존재 | schedule/teacher_availability_spec.md, availability_settings_ux_redesign_spec.md |
| D | 학생 초대·연결 | 가용 슬롯 존재 | 첫 학생과 관계 수립 (RelationshipStatus) | user/user_master.md §초대, lesson/invite/ |
| E | 수강권 제안·발급 | 관계 수립 | paymentConfirmed = true | subscription/subscription_master.md §3 |
| F | 스케줄 확인·확정 | 수강권 발급 | 학생 명시적 확인 → 정기 스케줄 확정 | schedule/schedule_confirmation_card_spec.md |
| G | 레슨 진행·노트 | 첫 레슨 시작 | 노트 작성·차감 완료 | lesson/lesson_master.md §5 |
| H | 일정 조절·갱신 | 정기 스케줄 운영 중 | 변경·취소·재등록 처리 | schedule/subscription_schedule_change_spec.md, lesson_cancellation_flow_spec.md |

### 단계 전이 게이트 (사이드 효과)

각 단계 사이에는 자동 처리되어야 하는 이벤트가 있다. 누락 시 사용자가 "왜 안 되지?" 혼선을 일으킨다.

| 전이 | 자동 처리 요구 |
|---|---|
| A → B | 신규 가입자 → 온보딩 Phase A 진입, 기존 사용자 → 홈 |
| B → C | "가용시간이 비어 있음" 알림이 홈 퀘스트 보드에 자동 등장 |
| C → D | 가용시간 있음 + 학생 0명 → "학생을 초대해보세요" 코치마크 |
| D → E | 첫 학생 연결 직후 → 수강권 제안 가이드 자동 표출 |
| E → F | paymentConfirmed → 학생 푸시 + 선생님 측 스케줄 확정 대기 표시 |
| F → G | 첫 레슨 D-1 → 노트 작성 준비 안내 |
| G → H | 수강권 만료 D-7 → 재등록·갱신 제안 자동 등장 |

## 4. 평가 차원 (5)

각 단계마다 다음 5차원으로 평가한다.

| # | 차원 | 핵심 질문 | 산출 |
|---|---|---|---|
| 1 | Drop-off (이탈) | 여기서 왜 포기하나? 어떤 외부 대안으로 도망가나? | 이탈 트리거 목록 |
| 2 | Friction (마찰) | 몇 번 탭? 몇 분? 입력 항목 수? | 탭/시간/필드 카운트 |
| 3 | Gap (누락) | 필요한데 스펙에 없거나 구현 안 된 기능? | 누락 카탈로그 |
| 4 | Conflict (갈등) | 스펙 간 충돌? FE-BE 명칭 불일치? glossary 위반? | 충돌 항목 |
| 5 | Benchmark (벤치마크) | 타서비스와 격차? 그들이 풀고 있는데 우리는 못 푸는 문제? | 격차 표 |

## 5. 우선순위 매트릭스

발견된 항목은 다음 매트릭스로 정렬한다.

```
                높은 임팩트       낮은 임팩트
              ┌──────────────┬──────────────┐
   저노력     │ 🔴 즉시 처리  │ 🟡 부수 작업  │
              ├──────────────┼──────────────┤
   고노력     │ 🟠 로드맵     │ ⚪ 보류       │
              └──────────────┴──────────────┘
```

- **임팩트** = 가입에서 첫 수강권 발급까지 도달 비율 (TTV 까지 포함) 에 미치는 영향
- **노력** =
  - 저: 스펙만 / 1-2시간 수정
  - 고: 스펙 + 코드 1주 이상 / DB 마이그레이션 / 백엔드 변경

각 항목은 `<id> <category> <stage> <dimension> <impact> <effort> <recommendation>` 형식으로 카탈로그화한다.

각 서비스는 모든 단계가 아닌, 그 서비스가 강한 단계만 본다.

| 클래스101 (강사) | 국내 콘텐츠 강사 | A, B | 강사 등록·노출 |

## 8. 실행 전략 — Subagent 병렬

본 검토는 컨텍스트 한도를 초과하므로 subagent 병렬 분산으로 진행한다.

| Agent | 담당 단계 | 입력 | 산출물 (200단어 이내) |
|---|---|---|---|
| Explore #1 | A, B (가입·온보딩) | user_master, teacher_onboarding_v3_spec | drop-off + friction + gap 목록 |
| Explore #2 | C, D (가용시간·학생초대) | schedule_master, availability spec, invite spec | 동일 포맷 |
| Explore #3 | E, F (수강권·확정) | subscription_master, schedule_confirmation_card_spec | 동일 포맷 |
| Explore #4 | G, H (레슨진행·일정조절) | lesson_master, subscription_schedule_change_spec, lesson_cancellation_flow_spec | 동일 포맷 |
| general-purpose #5 | 벤치마킹 | 위 10개 서비스 | 단계별 비교 표 |

메인 세션은 종합·의사결정·스펙 보완만 담당한다.

각 subagent 프롬프트는 다음을 포함한다.
- 본 plan 문서의 단계 정의
- 자신의 단계에 해당하는 스펙 파일 경로
- 5차원 평가틀
- subagent-output 규칙 (200단어 구조화 반환)

## 9. 의사결정 게이트

| Gate | 시점 | 결정 사항 |
|---|---|---|
| G1 | 펀넬 감사 + 벤치마크 완료 후 | 우선 처리할 Top 10 항목 확정 |
| G2 | 갭 카탈로그 완료 후 | 어디까지 본 세션에서 스펙 보완할지 / 새 세션으로 이월할지 |
| G3 | 스펙 보완 후 | 커밋 단위·PR 그룹핑 (도메인별 분리 vs 통합) |

## 10. 성공 기준

본 감사가 "성공"하려면 다음이 충족되어야 한다.

1. 8개 펀넬 단계 전체에 대해 5차원 평가가 작성됨
2. 발견된 갭 중 Critical/High 항목이 최소 5개 이상 식별됨
3. 각 갭에 대해 "기존 스펙 어디" 또는 "신규 스펙 어디"가 매핑됨
4. 타서비스 벤치마크가 최소 6개 서비스 × 우선 단계 표로 정리됨
5. Top 10 항목에 대해 사용자 승인이 G1 게이트에서 이루어짐

## 11. 비범위 (Out of Scope)

다음은 본 감사에서 다루지 않는다.

- 학생/학부모 페르소나 (다음 라운드)
- 디자인 시각 감사 (Notebook × Score 시스템은 별도 design 감사 영역)
- 백엔드 API 성능/보안 (security-reviewer 영역)
- 결제 모듈 자체 (외부 입금 모델은 결정 사항)
- 게이미피케이션·녹음 비교 등 보조 기능
