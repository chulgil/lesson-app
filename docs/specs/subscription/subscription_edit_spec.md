# 발급된 수강권 수정 스펙 (Subscription Post-Issuance Edit)

> 상태: 📋 설계 완료
> Last updated: 2026-05-07
> 관련: [subscription_master.md](./subscription_master.md), [lesson_policy_settings.md](./lesson_policy_settings.md), [lesson_location_management_spec.md](../schedule/lesson_location_management_spec.md)

**⚠️ 이 문서는 발급된 수강권의 수정/조정 기능의 Single Source of Truth입니다.**

---

## 1. 문제 정의

### 1.1 현재 상태

발급된 수강권은 사실상 **불변 계약** — 수정 가능한 것이 입금 확인, 일시정지, 변경권 소진뿐.

| 상황 | 선생님 요구 | 현재 대응 | 문제 |
|------|-----------|----------|------|
| "김민지 변경권 1회 더 줘야 해" | 변경권 추가 | ❌ 불가 | 새 수강권 발급해야 함 |
| "레슨 장소가 학생집→스튜디오로 바뀜" | 장소 변경 | ⚠️ 멤버십 레벨만 | 수강권에 반영 안 됨 |
| "이동시간이 20분→30분으로 늘었어" | 이동시간 수정 | ❌ 불가 | 스케줄 버퍼 업데이트 안 됨 |
| "취소 기준시간을 24시간→12시간으로" | 정책 수정 | ❌ 불가 | 발급 시 스냅샷 고정 |
| "레슨비를 5만원→6만원으로" | 금액 수정 | ❌ 불가 | 재발급 필요 |

### 1.2 유사 서비스 분석

| 서비스 | 발급 후 수정 | 배울 점 |
|--------|-----------|---------|
| **My Music Staff** | 수강권 수정 자유 (금액/횟수/기간) | 유연하지만 이력 관리 약함 |
| **Fons** | 패키지 수정 가능 (남은 횟수 조정) | 운영 편의 > 엄격한 계약 |
| **Teachworks** | 수강 패키지 편집 + 메모 | 변경 사유 기록 |
| **헬스장/요가원** | 일시정지 + 기간 연장 + 횟수 추가 | "서비스 연장" 개념 |
| **넷플릭스** | 플랜 업/다운그레이드 | 즉시 반영, 차액 정산 |
| **카카오T 패스** | 월 횟수 소진 시 추가 구매 | 추가 구매 ≠ 기존 수정 |

### 1.3 핵심 원칙

> **"수정 가능한 것"과 "재발급이 필요한 것"을 명확히 분리한다.**

| 구분 | 항목 | 이유 |
|------|------|------|
| **수정 가능** | 변경/취소권 추가, 레슨 장소, 이동시간, 정책(기준시간) | 운영상 빈번히 변경, 계약 핵심 조건 아님 |
| **재발급 필요** | 레슨 횟수, 금액, 기간, 레슨 시간(분) | 계약 핵심 조건, 변경 시 새 계약 = 새 수강권 |

## 2. 수정 가능 항목 — 상세 설계

### 2.1 변경/취소권 추가

> 가장 빈번한 요구. "학생이 사정이 있어서 1회 더 줘야 해."

```
┌─── 수강권 상세 > ⚙ 정책 ────────────────────┐
│                                              │
│  변경/취소권                                  │
│  현재: 1/2회 사용 (잔여 1회)                   │
│                                              │
│  [+ 추가]                                    │
│                                              │
│  → 바텀시트:                                  │
│  ┌────────────────────────────┐              │
│  │ 변경/취소권 추가             │              │
│  │                            │              │
│  │ 추가 횟수: [1] 회           │              │
│  │ 사유: [학생 사정 배려    ]   │              │
│  │                            │              │
│  │ [추가]                     │              │
│  └────────────────────────────┘              │
│                                              │
│  이력:                                        │
│  · 발급 시 2회 설정                            │
│  · 5/3 1회 사용 (3회차 변경)                   │
│  · 5/7 1회 추가 (사유: 학생 사정)              │
│  · 잔여 2회                                   │
└──────────────────────────────────────────────┘
```

**데이터 모델:**
```dart
// Subscription 확장
final int bonusRescheduleCount;  // 추가된 변경권 (기본 0)

// 계산
int get totalRescheduleAllowance =>
    _baseRescheduleAllowance + bonusRescheduleCount;
int get remainingReschedule =>
    totalRescheduleAllowance - usedRescheduleCount;
```

**이력 저장:** `RequestEvent(type: rescheduleCreditAdded, message: 사유)`

### 2.2 레슨 장소 + 이동시간 (통합 변경)

> 장소와 이동시간은 함께 변경되는 경우가 대부분. 하나의 플로우로 통합.

```
┌─── 수강권 상세 > ⚙ 정책 ────────────────────┐
│                                              │
│  레슨 장소 & 이동시간                          │
│  현재: 학생 집 (강남구 역삼동) · 25분           │
│                                       [변경] │
│                                              │
│  → 장소 변경 시트 열림:                        │
│  ┌──────────────────────────────────────┐    │
│  │ 장소 유형:                            │    │
│  │ [학생 집] [외부] [선생님 레슨실] [온라인]   │    │
│  │                                      │    │
│  │ 이동시간: [  30  ] 분                 │    │
│  │ (카카오 기준 약 25분 참고)             │    │
│  │                                      │    │
│  │ [저장]                               │    │
│  └──────────────────────────────────────┘    │
│                                              │
└──────────────────────────────────────────────┘
```

#### 이동시간 입력 원칙

> **API 제안 = 참고용. 선생님 입력값 = 확정값.**

```
이동시간 결정 흐름:

1. 수강권 발급 시:
   선생님 주소 + 학생 주소 → API 호출
   → 제안값 "약 25분" 자동기입
   → 선생님이 확인/수정 → [30] 분으로 확정
   → 이 30분이 스케줄 버퍼로 사용됨

2. 발급 후 장소 변경 시:
   새 장소 선택 → API 재호출
   → 제안값 "약 15분" 자동기입
   → 선생님이 확인/수정 → [20] 분으로 확정
   → 미래 레슨 스케줄 버퍼 업데이트

3. 이동시간만 수정 시:
   기존 제안값 참고 표시
   → 선생님이 직접 수정 → [35] 분으로 확정
```

| 단계 | API 제안 | 선생님 입력 | 확정값 |
|------|---------|-----------|--------|
| 발급 시 | 약 25분 (참고) | 30분 (수정) | **30분** |
| 장소 변경 | 약 15분 (참고) | 20분 (수정) | **20분** |
| 직접 수정 | — | 35분 | **35분** |
| API 실패 | 없음 | 25분 (직접) | **25분** |

> **핵심: `travelTimeMinutes`에 저장되는 값은 항상 선생님이 최종 확인한 값.**
> API 제안은 입력 편의를 위한 자동기입일 뿐, 시스템이 자동으로 확정하지 않음.

**변경 시 연쇄 업데이트:**
1. `ClassMembership.lessonLocationId` 변경
2. `ClassMembership.travelTimeMinutes` = **선생님 입력값** 저장
3. 미래 레슨의 스케줄 버퍼 재계산 (선생님 입력값 기준)

### 2.4 취소 기준시간 수정


## 3. 재발급이 필요한 항목

> 아래 항목은 계약 핵심 조건이므로 수정 불가. 변경 시 **갱신 제안(renewal)** 플로우로.

| 항목 | 이유 | 대안 |
|------|------|------|
| 레슨 횟수 | 금액과 직결 | 새 수강권 발급 (남은 횟수 참고) |
| 금액 | 계약 금액 변경 = 새 계약 | 새 수강권 발급 |
| 유효 기간 | 기간 연장 = 새 계약 | 새 수강권 발급 |
| 레슨 시간(분) | 수업 구조 변경 | 새 수강권 발급 |
| 수강권 타입 | 월정액↔회차권 전환 = 완전 다른 상품 | 새 수강권 발급 |

**안내 UX:**
```
"레슨 횟수나 금액을 변경하시려면
새 수강권을 발급해주세요."

[새 수강권 발급 →]   ← 갱신 제안 플로우로 이동
```

## 5. 변경/취소 기준시간 — 선생님 운영 가이드

### 5.1 선생님이 스케줄을 취소/변경할 때

| 시점 | 선생님 행동 | 학생 영향 | 변경권 |
|------|-----------|----------|--------|
| **24시간+ 전** | 자유롭게 취소/변경 | 학생에게 알림 | 차감 없음 (선생님 사유) |
| **24시간 이내** | 취소/변경 가능 (확인 다이얼로그) | 학생에게 긴급 알림 | 차감 없음 (선생님 사유) |
| **레슨 시작 후** | 취소 불가 (완료 또는 노쇼 처리) | — | — |

### 5.2 학생이 스케줄을 취소/변경할 때

| 시점 | 학생 행동 | 차감 | 변경권 |
|------|----------|------|--------|
| **기준시간+ 전** (기본 24h) | 사전 취소 | 횟수 유지 | 1회 사용 |
| **기준시간 이내** | 당일 취소 | **횟수 차감** | 1회 사용 |
| **미출석** | — | **횟수 차감** | 사용 없음 |
| **변경권 0회** | 변경 불가 → "선생님에게 문의" | — | — |

### 5.3 선생님이 학생 변경권을 돌려주는 경우

> 학생이 당일 취소했는데 선생님이 "괜찮아, 돌려줄게" 할 때.

기존 구현: `cancellationCreditRefunded` 이벤트 (이미 존재)
→ `usedRescheduleCount -= 1`
→ 챗에 "선생님이 변경/취소권을 돌려주었습니다" 표시

## 7. 데이터 모델 변경

### 7.1 Subscription 엔티티 확장

```dart
// 추가 필드
final int bonusRescheduleCount;       // 추가된 변경권 (기본 0)
final int? overrideCancelDeadlineHours; // 개별 취소 기준시간 (null = 기본 정책)

// 기존 필드 활용
final int totalRescheduleAllowance;   // 템플릿 기본값
final int usedRescheduleCount;
final int rescheduleDeadlineHours;

// 계산 변경
int get effectiveRescheduleAllowance =>
    totalRescheduleAllowance + bonusRescheduleCount;
int get remainingReschedule =>
    effectiveRescheduleAllowance - usedRescheduleCount;
int get effectiveCancelDeadlineHours =>
    overrideCancelDeadlineHours ?? rescheduleDeadlineHours;
```

## 9. Lore 결정

- **Lore-directive**: 변경권/장소/이동시간/기준시간은 발급 후 수정 가능. 횟수/금액/기간은 재발급 필요.
- **Lore-directive**: 이동시간은 장소 변경 시 자동 재측정 (선생님 주소 ↔ 학생 주소).
- **Lore-constraint**: 수정 이력은 RequestEvent로 기록 — 나중에 분쟁 시 증거.
- **Lore-rejected**: 모든 필드 자유 수정 — 계약 핵심 조건(횟수/금액)은 불변이 법적으로 안전.
- **Lore-rejected**: 수정 없이 전부 재발급 — 변경권 1회 추가 때문에 수강권 재발급은 과도함.

## 11. 학생 희망 장소 → 수강권 디폴트 연계

### 11.1 플로우

```
학생 레슨 신청 (UnifiedLessonRequest)
  └─ 희망 레슨 장소: "학생 집"   ← preferredLocationType
        ↓
선생님 승인 → 수강권 발급
  └─ 레슨 장소: "학생 집" (디폴트)  ← 학생 신청 값 자동 채움
        ↓
선생님이 장소 변경 시
  └─ ⚠ "학생이 신청 시 '학생 집'을 희망했습니다.
        장소를 변경하시겠습니까?"  ← 경고 표시
```

### 11.2 데이터 흐름

| 단계 | 필드 | 값 |
|------|------|-----|
| 학생 레슨 신청 | `UnifiedLessonRequest.preferredLocationType` | `"studentHome"` |
| 수강권 발급 시 | `LocationTravelSelector` 디폴트 | `preferredLocationType` 값으로 자동 선택 |
| 선생님 장소 변경 | 경고 다이얼로그 | "학생 희망 장소와 다릅니다" 안내 |
