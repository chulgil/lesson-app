## 1. 전체 구조 변경

### 1.1 레슨 요청 → 4단계 마무리

```
레슨 요청 라이프사이클 (변경 없음):
  신청 → 확정 → 입금 상태 → 완료(수강권 발급)

수강권 발급 후 → 별도 "수강권 관리" 화면으로 전환
```

### 1.2 홈 화면 재구성

```
[변경 전]                          [변경 후]
홈:                                홈:
├── 레슨 요청 섹션                  ├── 레슨 요청 섹션 (유지)
├── 수강권 섹션 ← 제거              ├── 스케줄 변경요청 섹션 ← NEW
└── 과제 요약                      └── 과제 요약

수강권 리스트 → 학생 상세 화면의 "수강권 현황"으로 이동
```

### 1.3 네비게이션 플로우

```
선생님 홈
├── 레슨 요청 (N) ─── 탭 → 레슨 요청 상세 (기존)
│
├── 스케줄 변경요청 (N) ─── 탭 → 스케줄 변경 상세 (NEW)
│   └── [전체보기] → 스케줄 변경요청 전체 목록
│
└── 학생 탭 → 학생 상세
    └── 수강권 현황
        └── 수강권 카드 탭 → 스케줄 변경 상세 (동일 화면)
```

### 2.3 회차 프로그레스 바 상세

> **LessonProgressBar와 pixel-exact 동일 패턴**

#### 배치 규칙
- **8개/줄** — 8회차 이하: 1줄, 9~16: 2줄, 17~24: 3줄
- 각 회차는 원형 인디케이터 (dot 20px, ring 28px)
- **[전체]** 버튼: 프로그레스 바 우측 끝 (월정액만)
- **커넥터**: `Expanded` — 모두 점선 (완료=primary, 미완료=borderLight)
- **패딩**: screenPadding (h), space2 (v) — 위젯 내부에서 적용

#### 상태별 표시

| 상태 | 시각 | 색상 | 라벨 |
|------|------|------|------|
| 완료 | filled circle + ✓ checkmark (12px) | **primary** | primary, normal |
| 다음 예정 (선택) | filled circle + outer ring (width 2) | **primary** + primaryLight ring | primary, w600 |
| 미래 | hollow circle (border 1.5px) | borderLight | textTertiaryLight, normal |
| 변경 요청 중 | warning dot (top-right 오버레이) | warning | — |

#### 자동 선택 규칙
- 화면 진입 시, **현재 일자 기준 다음에 진행할 회차**가 자동 선택
- 자동 선택된 회차의 챗 영역이 펼쳐지고 스크롤 위치 조정

#### [전체] 버튼 동작
```
[전체] 탭 시:
1. 현재~마지막 미완료 회차 전체 선택 (하이라이트)
2. 하단 버튼 라벨: "일정 변경" → "전체 스케줄 변경"
3. 일정 제안 시 말풍선: "전체 회차(4~10) 일정 변경을 제안했습니다"
4. 정규권에서만 활성화 (회차권은 비활성)
```

### 2.4 챗 영역 상세

#### 표시 내용
- **스케줄 변경 이벤트만 표시** (수강권 발급 카드 X)
- 각 회차별 스케줄 변경 요청/응답/확정 이벤트

#### 회차별 접기/펼치기

```
접힌 상태 (과거 완료):
  ── 1회차 · 4/5(토) 14:00 완료 ──     ← 한 줄 요약, 탭하면 펼침

펼쳐진 상태:
  ══ 4회차 · 4/26(토) 14:00 예정 ══    ← 강조 헤더
  │                                     │
  │  [학생 버블]                        │  스케줄 변경 챗 이벤트들
  │  "시간 변경 요청..."               │
  │                                     │
  │  [선생님 버블]                      │
  │  "가능한 시간..."                  │
  │                                     │
  ══════════════════════════════════     ← 회차 끝 구분선
```

#### 프로그레스 바 ↔ 챗 영역 연동
- 프로그레스 바에서 회차 탭 → 해당 회차 **펼침 + 자동 스크롤**
- 펼쳐진 회차가 있으면 기존 펼침 닫힘 (아코디언 방식)
- 과거 완료 회차도 탭하면 펼침 가능 (읽기 전용, 변경 불가)

### 2.6 일정 변경 말풍선 구조

> 디자인 계약: `docs/specs/design/detail_screen_template.md#채팅-히스토리-시각-문법`
>
> 레슨요청 상세와 스케줄 조절 상세는 같은 채팅 문법을 사용한다. 모든 사용자 이벤트는 viewer 기준 말풍선으로 렌더하고, 일정 후보/현재 일정/확정 일정만 말풍선 내부의 각진 사각형 일정 카드로 표시한다. 수락/거절/응답대기/결정변경/취소는 별도 성공/경고 박스를 만들지 않는다.

#### 학생 → 선생님 (변경 요청)
```
[학생 말풍선: 왼쪽/오른쪽은 viewer 기준]
"4회차 시간 변경을 요청합니다"
변경취소권 1회 사용 (잔여 1회)
┌────────────────────────┐
│ 1순위 일 10:00~11:00   │ [수락]
│ 2순위 월 14:00~15:00   │ [수락]
│ 3순위 화 10:00~11:00   │ [수락]
└────────────────────────┘
───────────
사유: 개인 일정 변경
```

#### 학생 → 선생님 (이번 일정 취소 요청)
```
[학생 말풍선]
"3회차 레슨 취소를 요청했어요"
변경/취소권 1회가 사용될 예정입니다. 잔여 1회
확정되면 이번 일정만 건너뛰고, 다음 진행 레슨이 3회차로 이어집니다.
───────────
사유: 컨디션이 좋지 않아 취소 요청드립니다
```

#### 취소 확정
```
[상대 말풍선]
"3회차 레슨이 취소되었습니다"
변경/취소권 1회가 사용되었습니다. 잔여 1회
수강권 회차는 차감되지 않으며, 다음 진행 레슨이 3회차입니다.
```

**취소/변경 의미 구분**
- `일정 변경`: 이번 회차를 진행할 대체 일정을 지금 조율한다.
- `이번 일정 취소`: 이번 일정은 건너뛰고 대체 일정은 나중에 정한다.
- 둘 다 학생 사유이면 변경/취소권을 1회 사용한다.
- 사전 취소는 수강권 회차를 차감하지 않는다. `N회차` 일정 취소 후 다음 실제 진행 레슨은 다시 `N회차`다.
- API 이벤트는 표시 시점의 현재 수강권 값이 아니라 이벤트 발생 시점의 변경/취소권 스냅샷을 제공해야 한다. 권장 필드: `changeCreditUsed`, `changeCreditRemainingAfter`, `keepsSessionNumber`. 히스토리 말풍선은 이 스냅샷을 우선 사용하고, mock/임시 구현에서만 현재 수강권 값으로 대체한다.

**상대 후보 응답 규칙**
- 학생과 선생님의 UI 구조는 동일하게 재사용할 수 있으나, 액션 권한은 `viewerRole` 기준으로 반드시 분리한다.
- 학생과 선생님의 액션 프로세스는 동일한 턴 기반 모델을 따르되, 각 역할이 수행할 수 있는 액션만 노출한다.
- 선생님 전용 액션: 수강권 직접 발급, 입금 확인, 무료/후불 수강권 발급, 선생님 수강권 템플릿 관리.
- 학생 전용 액션: 수강권 제안 확인/수락/거절, 입금 안내 확인, 입금 완료 알림, 선생님 응답 대기.
- 학생 화면에서는 `/subscriptions/issue` 또는 `IssueSubscriptionScreen`으로 진입할 수 없어야 하며, 실수로 해당 경로에 접근하면 학생용 수강권 목록/상세로 우회한다.
- 선생님 전용 수강권 라우트(`/subscriptions/issue`, `/subscriptions/templates`, `/subscriptions/teacher`, `/subscriptions/expiring`, `/schedule-change-requests`)는 공통 역할 가드로 보호한다. 학생/학부모가 직접 URL, 오래된 알림, 잘못 연결된 CTA로 접근해도 선생님 액션 화면을 렌더링하지 않는다.
- 학생 홈의 레슨 카드/수강권 카드처럼 학생 전용 진입점에서 상세 화면으로 이동할 때는 `viewerRole=student`를 명시적으로 전달한다. 라우터의 기본값이나 현재 디버그 역할 상태에 암묵적으로 의존하지 않는다.
- 상대가 `suggestedSlots`를 포함해 시간 변경 요청/제안을 보낸 경우, 말풍선은 히스토리 표시만 담당하고 하단 액션바가 레슨요청 UI와 같은 상태 기반 응답 UI로 전환된다.
- 하단 액션바는 `일정을 탭하여 선택하세요` 안내, 1/2/3순위 슬롯 칩, 메시지 입력, `수락` 버튼을 표시한다.
- 하단의 `일정 변경` 버튼은 내가 새 변경 요청/제안을 시작할 때만 사용한다. 상대가 이미 후보를 보낸 상태에서 수락하려고 새 변경 플로우를 다시 시작하지 않는다.
- 수락 시 같은 `subscriptionId + sessionNumber`에 `scheduleChangeAccepted` 이벤트를 추가한다.
- `scheduleChangeAccepted` 이벤트는 원 요청/제안의 `suggestedSlots`와 `selectedSlotIndex`를 보존해야 하며, 확정 말풍선에서 선택된 시간 라벨을 재현할 수 있어야 한다.
- 내가 수락한 뒤에는 하단 액션바가 `상대방의 응답을 기다리고 있습니다` + `결정 변경` 상태로 바뀐다.
- `결정 변경`을 누르면 `withdrawApproval` 이벤트를 남기고, 이전에 수락했던 슬롯 라벨은 히스토리 말풍선에서 취소선 처리한다.
- 결정 변경 후에는 레슨요청 UI와 동일하게 다시 슬롯을 선택해 수락하거나 다른 결정을 진행할 수 있어야 한다.

#### 선생님 → 학생 (시간 제안)
```
[선생님 말풍선]
"4회차 일정 변경을 제안했습니다"
┌────────────────────────┐
│ 1순위 일 10:00~11:00   │
│ 2순위 월 14:00~15:00   │
│ 3순위 화 10:00~11:00   │
└────────────────────────┘
메시지: "일요일 오전이 가장 여유있습니다"
```

#### 전체 회차 변경 시
```
[선생님 말풍선]
"전체 회차(4~10) 일정 변경을 제안했습니다"
┌────────────────────────┐
│ 1순위 매주 일 10:00~11:00  │  ← 매주 반복 슬롯
│ 2순위 매주 월 14:00~15:00  │
│ 3순위 매주 화 10:00~11:00  │
└────────────────────────┘
메시지: "일요일 오전이 가장 여유있습니다"
```

> **UI 통일 원칙**: "이번 회차만"과 "앞으로 모두" 모두 동일한 `ScheduleChangeSlotScreen`
> (선생님 빈 시간대 그리드)을 사용한다. 최대 3개 후보 제안, 상대방이 1개 수락 시 확정.
> - 이번 회차만: 선택 슬롯 = 해당 회차의 새 시간
> - 앞으로 모두: 선택 슬롯의 요일+시간 = 매주 반복 고정 스케줄 (수락 시 적용)

#### 학생 수락
```
[학생 말풍선]
"1순위 일 10:00~11:00을 선택했습니다"
4회차 → 4/27(일) 10:00 확정
```

#### 선생님 수락
```
[선생님 말풍선]
"2순위 월 14:00~15:00을 선택했습니다"
4회차 → 월 14:00 확정
```

> **중요**: 수락 주체는 상대가 제시한 후보를 선택한 사람이다.
> - 학생 요청(`scheduleChanged`, actor=student, `suggestedSlots` 있음) → 선생님이 후보 중 하나를 수락
> - 선생님 제안(`scheduleChangeProposed`, actor=teacher, `suggestedSlots` 있음) → 학생이 후보 중 하나를 수락
> 따라서 화면 정렬은 viewer 기준이지만, 하단 액션바 상태는 최신 스케줄 이벤트의 `actorType`, `eventType`, `suggestedSlots`, `selectedSlotIndex`로 판단한다.

#### 수락 후 응답 대기 / 결정 변경
```
[내 말풍선]
"2순위 월 14:00~15:00을 선택했습니다"

[하단 액션바]
⏳ 김선아님의 응답을 기다리고 있습니다
[결정 변경]
```

#### 시간변경 제안 후 응답 대기 / 결정 변경
```
[내 말풍선]
"4회차 일정 변경을 제안했습니다"
┌────────────────────────┐
│ 1순위 일 10:00~11:00   │
│ 2순위 월 14:00~15:00   │
│ 3순위 화 10:00~11:00   │
└────────────────────────┘

[하단 액션바]
⏳ 김민준님의 응답을 기다리고 있습니다
[결정 변경]
```

규칙:
- 내가 `scheduleChanged`, `scheduleChangeProposed`, `scheduleChangeCountered`, `scheduleChangeAccepted`로 시간변경 후보 또는 수락 결정을 보낸 직후에는 일반 `일정 변경 / 메시지 전송` 입력 상태로 돌아가지 않는다.
- 레슨요청에서 요청 수락/대안 수락 후와 동일하게 `상대방님의 응답을 기다리고 있습니다` + `결정 변경`을 표시한다.
- `결정 변경`은 내가 방금 보낸 후보 이벤트를 대상으로 `withdrawApproval`을 남긴다.
- 상대가 보낸 후보 이벤트만 `일정을 탭하여 선택하세요` + `일정 비교` + `수락` 상태로 표시한다.
- 하단 액션바의 최신 이벤트 판정은 `eventType`, `actorType`, `suggestedSlots`, `selectedSlotIndex`를 함께 본다. 단순히 `pending/completed` 플래그만으로 버튼을 결정하지 않는다.

#### 결정 변경 히스토리
```
[내 말풍선]
"결정을 변경했습니다"
~~월 14:00~15:00~~
```

> `withdrawApproval` 이벤트는 이전 `scheduleChangeAccepted`의 `suggestedSlots`와 `selectedSlotIndex`를 보존한다.
> 그래야 취소선 처리할 기존 날짜/시간을 정확히 복원할 수 있다.
>
> 금지: 수락 이벤트만 초록 체크 아이콘/성공 Row로 렌더하거나, 결정 변경 이벤트만 별도 안내 박스로 렌더하는 방식.

## 3. 홈 화면 — 스케줄 변경요청 섹션

### 3.1 섹션 구조

```
┌──────────────────────────────────────┐
│  📅 스케줄 변경요청 (3)   [전체보기]  │ 헤더
│  변경 2 · 취소 1                     │ 상태 요약
│                                      │
│  ┌────────────────────────────────┐ │ 변경요청 미니 카드
│  │ 🔵 김소연 4회차 시간변경 · 2시간│ │
│  │ 🔴 이민수 5회차 취소   · 30분  │ │
│  │ 🔵 박지현 3회차 시간변경 · 1일 │ │
│  └────────────────────────────────┘ │
└──────────────────────────────────────┘
```

### 3.2 미니 카드 탭 동작
- 탭 → 스케줄 변경 상세 화면 진입 (해당 회차 자동 선택)

### 3.3 전체보기 화면

```
┌──────────────────────────────────────┐
│  ← 스케줄 변경요청                    │ AppBar
├──────────────────────────────────────┤
│  [대기중] [완료] [전체]               │ 상태 탭
├──────────────────────────────────────┤
│  [1주] [1달] [3달]                    │ 기간 필터
├──────────────────────────────────────┤
│  김소연 · 8회권                       │ 리스트 아이템
│  4회차 · 시간변경                     │
│  화 18:00~19:00 외 2건                │
│                         확인 필요 · 2시간 전│
│  ─────────────────────────────────  │
│  이민수 · 월 4회권                    │
│  5회차 · 취소                         │
│  사유 메시지 요약                     │
│                         응답 대기 · 30분 전│
└──────────────────────────────────────┘
```

규칙:
- 레슨요청 전체화면과 동일한 정보 구조를 따른다. 현재 구현 기준은 `대기중/완료/전체` 탭 + `1주/1달/3달` 기간 필터 + 리스트이며, 추후 캘린더/단계 필터가 들어가더라도 학생명/상태/회차/후보 요약 계약은 유지한다.
- 스케줄 변경 상세 화면의 `Scaffold.backgroundColor`는 레슨요청 상세와 동일하게 `AppColors.paper`로 고정한다. 상세 배경, 채팅 영역, 하단 액션바가 서로 다른 기본 Material 배경색으로 분리되어 보이면 안 된다.
- 리스트 탭은 `대기중/완료/전체`일 수 있으나, 아이템 상태 스탬프는 단순 `대기중`이 아니라 `확인 필요`, `응답 대기`, `완료`로 분리한다.
- `확인 필요`: viewer 기준 상대가 보낸 `scheduleChanged`, `lessonCancelled`, `scheduleChangeProposed`, `scheduleChangeCountered`.
- `응답 대기`: viewer 기준 내가 보낸 후보/요청/수락 이벤트이며 상대 응답이 아직 필요한 상태.
- `완료`: `scheduleChangeAccepted`, `scheduleChangeRejected`.
- 리스트의 학생명은 `event.actorId`가 아니라 `subscriptionId → subscription.studentId → studentName`으로 해석한다. 선생님이 보낸 제안 이벤트에서도 대상 학생명이 표시되어야 한다.
- 카드 정보 구조는 홈 스케줄 변경 미니 카드와 레슨요청 `RequestListItem`의 공통 패턴을 따른다: 아바타, 상단 메타, 학생명+수강권 타입, 후보 일정 요약, 우측 상태 스탬프+상대 시간.
- 레슨 취소(`lessonCancelled`)는 모든 노출 지점에서 `sessionNumber`를 포함한다. 채팅 말풍선/진행탭/목록은 각각 `N회차 레슨 취소를 요청했어요`, `N회차 레슨이 취소되었습니다`, `N회차 · 취소요청`처럼 회차가 먼저 읽혀야 한다.
- Mock/API 이벤트의 `sessionNumber`는 연결된 수강권의 총회차 경계 안에 있어야 한다. 예: 월 4회권에는 5회차 변경/취소 이벤트를 연결하지 않는다. 5회차 경계 테스트가 필요하면 5회차 이상 수강권에 연결한다.
- 목록에서 상세로 진입할 때는 `subscriptionId`뿐 아니라 `sessionNumber`를 route query로 넘긴다. 상세 화면은 해당 회차가 현재 완료/다음 회차보다 미래여도 deep-link 회차를 보이게 해야 한다.
- 목록과 상세 채팅은 동일한 이벤트 SSOT를 사용한다. mock 구현에서도 `pendingScheduleChangeRequestsProvider`와 `subscriptionSessionEventsProvider(subscriptionId, sessionNumber)`가 같은 `RequestEvent.id`를 반환해야 하며, 한쪽에만 존재하는 mock 이벤트를 금지한다.

## 7. 데이터 플로우

```
[이벤트 저장]
  학생/선생님 액션 → RequestEvent 생성
    - subscriptionId
    - sessionNumber (또는 null = 전체)
    - eventType (scheduleChangeRequested / Proposed / Accepted / Countered)
    - suggestedSlots (시간 제안 시)
    - message (텍스트 메시지)

[화면 로딩]
  pendingScheduleChangeRequestsProvider(viewerId) → 목록
  subscriptionSessionEventsProvider(subscriptionId, sessionNumber) → 상세 회차 히스토리
  두 provider는 같은 RequestEvent SSOT를 기준으로 동작
  → subscriptionId + sessionNumber 매칭 → 회차별 챗 렌더링

[상세 진입]
  /subscriptions/:id?session=N
  → selectedSession=N
  → N회차 펼침 + 해당 회차 이벤트 렌더링
```

### 7.1 Mock/API 경계 테스트 필수 케이스

개발/QA mock 데이터는 단순 샘플이 아니라 경계 테스트 데이터다. 최소 아래 케이스를 유지한다.

| 케이스 | 필수 필드 |
|------|----------|
| 학생이 단일 회차 변경 요청 | `actorType=student`, `eventType=scheduleChanged`, `suggestedSlots` 3개, `sessionNumber` |
| 선생님이 단일 회차 변경 제안 | `actorType=teacher`, `eventType=scheduleChangeProposed`, `suggestedSlots` 3개, `sessionNumber` |
| 전체 스케줄 변경 요청 | `scheduleChangeType=bulkChange`, `proposedDayOfWeek`, `proposedTime`, `suggestedSlots` 3개 |
| 학생/선생님 중 한쪽이 수락 | `eventType=scheduleChangeAccepted`, 원 후보 `suggestedSlots`, `selectedSlotIndex` |
| 결정 변경 | `eventType=withdrawApproval`, 취소선 복원을 위한 원 후보 `suggestedSlots`, `selectedSlotIndex` |
| 취소 요청 | `eventType=lessonCancelled`, `sessionNumber`, 취소/변경권 사용 예정 문구에 필요한 스냅샷 |

검증 규칙:
- 모든 mock `subscriptionId`는 실제 mock 수강권에 존재해야 한다.
- 학생 actor 이벤트는 해당 actor 학생이 가진 수강권을 가리켜야 한다.
- 모든 `sessionNumber`는 해당 수강권의 `totalLessons` 또는 `lessonsPerMonth` 이하이어야 한다.
- 일정변경 목록 provider의 모든 이벤트는 같은 `(subscriptionId, sessionNumber)` 상세 이력 provider에서도 조회되어야 한다.
