## 1. 개요

### 1.1 배경

lesson-app은 현재 **개인 선생님**을 위한 레슨 관리 앱으로 설계되어 있습니다.
스튜디오메이트와 같은 학원 관리 시스템의 수강권 기능을 도입하면서,
**개인 선생님**과 **학원** 모두 사용할 수 있는 구조로 확장합니다.

### 1.2 핵심 목표

| 목표 | 설명 |
|------|------|
| 하위 호환성 | 기존 개인 선생님 사용자 영향 없음 |
| 학원 지원 | 다중 강사, 역할별 권한, 수강권 관리 |
| 법적 안정성 | 개인정보보호법, 저작권법 준수 |
| 단순한 정산 | 앱은 기록만, 실제 정산은 외부 처리 |

### 1.3 설계 결정 요약

| 항목 | 결정 | 근거 |
|------|------|------|
| 계정 타입 | 개인/학원 **분리 가입** | 명확한 구분, UX 단순화 |
| 데이터 소유권 | **3자 공동** (학원+강사+학생) | 모든 이해관계자 권익 보호 |
| 퇴사 후 접근 | **즉시 차단** | 개인정보보호법 준수 |
| 역할 체계 | **3단계** (대표/매니저/강사) | 스튜디오메이트 참고, 현실적 운영 |
| 정산 범위 | **기록만** | 복잡도 최소화, CS 감소 |
| Export 방식 | **PDF + JSON** | 열람용 + 백업용 모두 지원 |
| 플랫폼 | **앱 + 웹 분리** | 역할별 최적화 (레슨=앱, 학원관리=웹) |
| 다중 소속 | **지원** | 선생님 여러 학원, 학생 병행 레슨 |

## 2. 설계 원칙

### 2.1 핵심 원칙

```
1. "organizationId가 null이면 개인, 있으면 학원"
   - 모든 주요 엔티티에 동일 패턴 적용
   - 개인 모드 코드 변경 최소화

2. "돈은 앱 밖에서, 기록은 앱 안에서"
   - 결제/정산은 학원 내부 또는 외부 시스템
   - 앱은 수강권 판매/사용 기록만 관리

3. "강사 퇴사 = 권한 회수, 기록 보존"
   - 학원 데이터 연속성 보장
   - 강사는 퇴사 전 본인 기록 export 가능

4. "다중 소속 지원" ⭐ 신규
   - 선생님: 여러 학원 소속 + 개인 레슨 병행 가능
   - 학생: 학원 레슨 + 개인 레슨 병행 가능
   - 레슨 기록 시 Context(학원/개인) 선택
```

### 2.2 플랫폼 분리: 앱 + 웹

역할별 사용 맥락이 다르므로 **앱과 웹을 분리**합니다.

```
┌─────────────────────────────────────────────────────────────┐
│                     lesson-app 플랫폼 구조                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   [lesson-app 앱]                [lesson-app 웹] (신규)      │
│   (Flutter - 기존 유지)           (웹 - 별도 개발)            │
│                                                             │
│   👤 개인 선생님                  🏫 학원 대표/매니저          │
│   👨‍👩‍👧 학부모                       • 학원 설정               │
│   🎓 학생                         • 강사 초대/관리            │
│   👨‍🏫 학원 강사 (레슨 기록)         • 수강권 발행             │
│                                   • 정산 리포트              │
│   • 레슨 기록                     • 학생 배정                │
│   • 연습 (메트로놈/튜너/녹음)       • 매출 분석               │
│   • 수강권 확인                                              │
│   • 알림                                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 플랫폼 분리 이유

| 역할 | 주요 사용 상황 | 적합한 플랫폼 |
|------|--------------|--------------|
| **학생/학부모** | 이동 중, 연습 중 | 📱 모바일 앱 |
| **개인 선생님** | 레슨 중 기록 | 📱 모바일 앱 |
| **학원 강사** | 레슨 기록 | 📱 모바일 앱 |
| **학원 대표/매니저** | 정산, 리포트, 관리 | 💻 웹 |

#### 공유 요소

| 항목 | 공유 방식 |
|------|----------|
| 백엔드 API | 동일한 FastAPI 서버 |
| 인증 | 동일한 계정 (앱/웹 모두 로그인) |
| 데이터 | 동일한 DB |
| 디자인 토큰 | 색상, 타이포그래피 공유 |

### 2.3 스튜디오메이트와의 차별점

| 항목 | 스튜디오메이트 | lesson-app |
|------|--------------|------------|
| 타겟 | 피트니스 학원 전용 | 개인 선생님 + 음악 학원 |
| 앱 구조 | 관리자/회원 앱 분리 | **앱(레슨) + 웹(학원관리)** |
| 레슨 기록 | 출석만 | **레슨 노트, 녹음, 과제** |
| 연습 도구 | 없음 | **메트로놈, 튜너, 녹음** |
| 학부모 연동 | 없음 | **학부모 앱** |
| 선생님 다중 소속 | 미확인 | **여러 학원 + 개인 병행** |

## 3. 계정 타입 및 역할 체계

### 3.1 다중 소속 구조 (핵심)

선생님은 **여러 학원에 소속**될 수 있고, 학생은 **학원 레슨 + 개인 레슨을 병행**할 수 있습니다.

#### 현실 시나리오

```
[선생님 A]
    │
    ├── OO음악학원 소속 (강사)
    │   └── 학생 1, 2, 3 (학원 수강생)
    │
    ├── XX피아노학원 소속 (강사)
    │   └── 학생 4, 5 (학원 수강생)
    │
    └── 개인 레슨
        └── 학생 6, 7 (개인 수강생)


[학생 B]
    │
    ├── OO음악학원에서 바이올린 레슨 (선생님 A)
    │   └── 8회권 수강권
    │
    └── 개인적으로 피아노 레슨 (선생님 C) ← 학원과 무관
        └── 월정액 수강권
```

#### 관계 모델

```
기존 (1:1 관계):
Teacher ─── Student

변경 (N:M 관계 + Context):
Teacher ──┬── Membership ──── Organization (학원)
          │
          └── TeacherStudentRelation ── Student
                    │
                    ├── organizationId (nullable: null이면 개인)
                    ├── subscriptionId (연결된 수강권)
                    └── instrument (악기)
```

### 3.2 계정 타입

```

│                       lesson-app 계정                        │
├────────────────────────────┬────────────────────────────────┤
```

### 3.3 학원 역할 체계 (3단계)

| 역할 | 설명 | 주요 권한 |
|------|------|----------|
| **대표 (Owner)** | 학원 개설자, 최고 관리자 | 모든 권한, 학원 설정, 역할 변경 |
| **매니저 (Manager)** | 운영 담당자 | 학생 배정, 수강권 발행, 매출 조회 |
| **강사 (Instructor)** | 레슨 담당 강사 | 배정된 학생만 관리, 레슨 기록 |

## 4. 데이터 소유권 정책

### 4.1 기본 원칙: 3자 공동 소유

레슨 기록은 **학원/선생님**, **학생** 모두에게 소유권이 있습니다.
학생은 비용을 지불하고 받은 레슨이므로, 선생님이 탈퇴해도 본인 기록을 계속 열람할 수 있습니다.

```
┌─────────────────────────────────────────────────────────────┐
│                    데이터 소유권 구조 (3자)                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│      [학원/선생님]                    [학생/학부모]           │
│           │                              │                  │
│           │         공동 소유            │                  │
│           └────────────┬─────────────────┘                  │
│                        │                                    │
│                   [레슨 기록]                                │
│                        │                                    │
│           ┌────────────┼────────────┐                       │
│           ▼            ▼            ▼                       │
│      선생님 탈퇴    학생 탈퇴    선생님 변경                   │
│      → 학생 계속    → 선생님    → 새 선생님은                 │
│         열람 가능     보관 유지     학생 승인 필요             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 레슨 기록 공개 범위 (3단계)

학생이 자신의 레슨 기록 공개 범위를 설정할 수 있습니다.

| 공개 레벨 | 아이콘 | 설명 | 열람 가능자 |
|----------|:------:|------|------------|
| **전체 공개** | 🌐 | 누구나 열람 가능 | 모든 사용자 |
| **현재 선생님만** | 👤 | 담당 선생님만 열람 | 현재 담당 선생님 |
| **비공개** | 🔒 | 본인만 열람 | 학생/학부모만 |

### 4.3 데이터 유형별 기본 공개 설정

| 데이터 유형 | 기본값 | 변경 가능 | 설명 |
|------------|--------|:--------:|------|
| **레슨 노트** | 👤 현재 선생님 | ✅ | 학습 내용 |
| **레퍼토리 목록** | 🌐 전체 공개 | ✅ | 포트폴리오 성격 |
| **녹음 파일** | 🔒 비공개 | ✅ | 개인 연습 민감 |
| **연습 기록** | 👤 현재 선생님 | ✅ | 과제 확인 |
| **연락처** | 🔒 비공개 | ❌ | 개인정보 (변경 불가) |
| **결제 정보** | 🔒 비공개 | ❌ | 개인정보 (변경 불가) |

### 5.6 외부 결제 관리 (계좌이체/현금)

우리 시스템은 **결제가 외부**에서 이루어지므로, 결제 기록만 관리합니다.

#### 타사 서비스 결제 처리 방식 비교

| 방식 | 설명 | 예시 서비스 |
|------|------|------------|
| **PG 연동형** | 앱 내 카드/간편결제 → 자동 수납 | 결제선생, 스튜디오메이트 |
| **결제 기록형** | 외부 결제 후 수동 "결제 확인" | 대부분의 학원 관리 시스템 |
| **청구서형** | 청구서 발송 후 결제 확인 대기 | 결제선생 알림톡 |

#### 결제 방법별 처리

| 결제 방법 | 처리 방식 | Payment.method |
|-----------|----------|----------------|
| 카드 (외부) | 매니저가 수동 확인 후 기록 | `card` |
| 계좌이체 | 입금 확인 후 "결제 확인" 처리 | `transfer` |
| 현금 | 수령 후 "결제 확인" 처리 | `cash` |
| 미수금 | 수강권 먼저 발행, 나중에 결제 확인 | - |

#### 가족(자녀 2명 이상) 수강권 시나리오

```
학부모 김OO
├── 자녀1: 김민수 (바이올린)
└── 자녀2: 김서연 (피아노)
```

**처리 플로우**:

| 단계 | 위치 | 담당자 | 작업 |
|------|------|--------|------|
| 1 | 외부 | 학부모 | 40만원 계좌이체 (20만원 × 2명) |
| 2 | **웹** | 학원 매니저 | 입금 확인 |
| 3 | **웹** | 학원 매니저 | Payment 1건 생성 (40만원, transfer) |
| 4 | **웹** | 학원 매니저 | 김민수 Subscription 발행 (20만원) |
| 5 | **웹** | 학원 매니저 | 김서연 Subscription 발행 (20만원) |
| 6 | **앱** | 학부모 | 자녀들 수강권 현황 조회 |
| 7 | **앱** | 선생님 | 레슨 시 해당 학생 수강권 차감 |

**핵심 원칙**:
- 수강권은 **학생별** 발급 (Subscription.studentId)
- Payment는 **통합 결제 기록**으로 사용 가능
- 여러 Subscription이 하나의 Payment를 참조할 수 있음

```dart
// Payment - 통합 결제 기록
Payment {
  id: "pay_001",
  amount: 400000,           // 40만원 (2명분)
  method: PaymentMethod.transfer,
  status: PaymentStatus.confirmed,
}

// Subscription #1 - 김민수
Subscription {
  studentId: "김민수",
  paymentId: "pay_001",     // 동일한 Payment 참조
  amount: 200000,
}

// Subscription #2 - 김서연
Subscription {
  studentId: "김서연",
  paymentId: "pay_001",     // 동일한 Payment 참조
  amount: 200000,
}
```

### 6.4 왜 정산을 앱에서 안 하는가?

| 이유 | 설명 |
|------|------|
| **법적 복잡도** | PG 연동 시 전자금융업 등록 필요 가능성 |
| **CS 부담** | 정산 분쟁 발생 시 중재 역할 부담 |
| **업계 관행** | 학원-강사 정산은 계약에 따라 다양 (5:5, 6:4 등) |
| **개발 복잡도** | PG 연동, 정산 시스템 개발 비용 |

> **참고**: 바디코디, My Music Staff도 **계산 기능만 제공**하고 실제 지급은 외부 처리

### 8.2 Membership (학원-강사 관계) - 다중 소속 지원

선생님은 **여러 학원에 소속**될 수 있습니다.

```dart
/// 학원 멤버십 (선생님 1명 → 여러 학원 가능)
class Membership {
  final String id;
  final String organizationId;          // 학원 ID
  final String userId;                  // 선생님 ID
  final MemberRole role;
  final MemberStatus status;
  final DateTime joinedAt;
  final DateTime? terminatedAt;
  final String? terminatedBy;           // 퇴사 처리자
  final TerminationReason? terminationReason;
}

// 예시: 선생님 A가 2개 학원 소속
// Membership { organizationId: "OO음악학원", userId: "선생님A", role: instructor }
// Membership { organizationId: "XX피아노학원", userId: "선생님A", role: instructor }

enum MemberRole {
  owner,       // 대표: 모든 권한
  manager,     // 매니저: 학생 배정, 수강권 발행
  instructor,  // 강사: 배정된 학생만
}

enum MemberStatus {
  active,      // 활성
  inactive,    // 비활성 (일시 중지)
  terminated,  // 퇴사
}

enum TerminationReason {
  resignation,   // 자진 퇴사
  dismissal,     // 해고
  contractEnd,   // 계약 종료
  other,
}
```

### 8.3 TeacherStudentRelation (선생님-학생 관계) - Context 포함

```dart
/// 선생님-학생 관계 (Context 포함)
class TeacherStudentRelation {
  final String id;
```

```dart
/// 권한 체크 서비스
class PermissionService {

  /// 학생 접근 권한 확인
  Future<bool> canAccessStudent(String userId, String studentId) async {
    final student = await getStudent(studentId);

    // 개인 모드
    if (student.organizationId == null) {
      return student.teacherId == userId;
    }

    // 학원 모드
    final membership = await getMembership(userId, student.organizationId!);
    if (membership == null) return false;

    switch (membership.role) {
      case MemberRole.owner:
      case MemberRole.manager:
        return true;  // 전체 학생 접근 가능
      case MemberRole.instructor:
        return student.assignedInstructorId == userId;  // 담당 학생만
    }
  }

  /// 수강권 발행 권한 확인
  Future<bool> canIssueSubscription(String userId, String? orgId) async {
    if (orgId == null) return true;  // 개인 모드는 항상 가능

    final membership = await getMembership(userId, orgId);
    if (membership == null) return false;

    return membership.role == MemberRole.owner ||
           membership.role == MemberRole.manager;
  }
}
```

- PC 대량 청구서 발송 가능
- 1~3일 빠른 정산

**적합 대상**: 비대면 청구서 결제가 필요한 소규모 학원

**적합 대상**: 학원관리 + 결제를 통합하려는 중대형 학원
