## 1. 개요

### 1.1 배경

lesson-app은 현재 **개인 선생님**을 위한 레슨 관리 앱으로 설계되어 있습니다.
스튜디오메이트와 같은 학원 관리 시스템의 수강권 기능을 도입하면서,
**개인 선생님**과 **학원** 모두 사용할 수 있는 구조로 확장합니다.

### 1.2 핵심 목표

| 목표 | 설명 |
|------|------|
| 하위 호환성 | 기존 개인 선생님 사용자 영향 없음 |
| 학원 지원 | 다중 강사, 역할별 권한, 수강권 관리 |
| 법적 안정성 | 개인정보보호법, 저작권법 준수 |
| 단순한 정산 | 앱은 기록만, 실제 정산은 외부 처리 |

### 1.3 설계 결정 요약

| 항목 | 결정 | 근거 |
|------|------|------|
| 계정 타입 | 개인/학원 **분리 가입** | 명확한 구분, UX 단순화 |
| 데이터 소유권 | **3자 공동** (학원+강사+학생) | 모든 이해관계자 권익 보호 |
| 퇴사 후 접근 | **즉시 차단** | 개인정보보호법 준수 |
| 역할 체계 | **3단계** (대표/매니저/강사) | 스튜디오메이트 참고, 현실적 운영 |
| 정산 범위 | **기록만** | 복잡도 최소화, CS 감소 |
| Export 방식 | **PDF + JSON** | 열람용 + 백업용 모두 지원 |
| 플랫폼 | **앱 + 웹 분리** | 역할별 최적화 (레슨=앱, 학원관리=웹) |
| 다중 소속 | **지원** | 선생님 여러 학원, 학생 병행 레슨 |

## 2. 설계 원칙

### 2.1 핵심 원칙

```
1. "organizationId가 null이면 개인, 있으면 학원"
   - 모든 주요 엔티티에 동일 패턴 적용
   - 개인 모드 코드 변경 최소화

2. "돈은 앱 밖에서, 기록은 앱 안에서"
   - 결제/정산은 학원 내부 또는 외부 시스템
   - 앱은 수강권 판매/사용 기록만 관리

3. "강사 퇴사 = 권한 회수, 기록 보존"
   - 학원 데이터 연속성 보장
   - 강사는 퇴사 전 본인 기록 export 가능

4. "다중 소속 지원" ⭐ 신규
   - 선생님: 여러 학원 소속 + 개인 레슨 병행 가능
   - 학생: 학원 레슨 + 개인 레슨 병행 가능
   - 레슨 기록 시 Context(학원/개인) 선택
```

### 2.2 플랫폼 분리: 앱 + 웹

역할별 사용 맥락이 다르므로 **앱과 웹을 분리**합니다.

```
┌─────────────────────────────────────────────────────────────┐
│                     lesson-app 플랫폼 구조                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   [lesson-app 앱]                [lesson-app 웹] (신규)      │
│   (Flutter - 기존 유지)           (웹 - 별도 개발)            │
│                                                             │
│   👤 개인 선생님                  🏫 학원 대표/매니저          │
│   👨‍👩‍👧 학부모                       • 학원 설정               │
│   🎓 학생                         • 강사 초대/관리            │
│   👨‍🏫 학원 강사 (레슨 기록)         • 수강권 발행             │
│                                   • 정산 리포트              │
│   • 레슨 기록                     • 학생 배정                │
│   • 연습 (메트로놈/튜너/녹음)       • 매출 분석               │
│   • 수강권 확인                                              │
│   • 알림                                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 플랫폼 분리 이유

| 역할 | 주요 사용 상황 | 적합한 플랫폼 |
|------|--------------|--------------|
| **학생/학부모** | 이동 중, 연습 중 | 📱 모바일 앱 |
| **개인 선생님** | 레슨 중 기록 | 📱 모바일 앱 |
| **학원 강사** | 레슨 기록 | 📱 모바일 앱 |
| **학원 대표/매니저** | 정산, 리포트, 관리 | 💻 웹 |

#### 공유 요소

| 항목 | 공유 방식 |
|------|----------|
| 백엔드 API | 동일한 FastAPI 서버 |
| 인증 | 동일한 계정 (앱/웹 모두 로그인) |
| 데이터 | 동일한 DB |
| 디자인 토큰 | 색상, 타이포그래피 공유 |

### 2.3 스튜디오메이트와의 차별점

| 항목 | 스튜디오메이트 | lesson-app |
|------|--------------|------------|
| 타겟 | 피트니스 학원 전용 | 개인 선생님 + 음악 학원 |
| 앱 구조 | 관리자/회원 앱 분리 | **앱(레슨) + 웹(학원관리)** |
| 레슨 기록 | 출석만 | **레슨 노트, 녹음, 과제** |
| 연습 도구 | 없음 | **메트로놈, 튜너, 녹음** |
| 학부모 연동 | 없음 | **학부모 앱** |
| 선생님 다중 소속 | 미확인 | **여러 학원 + 개인 병행** |

## 3. 계정 타입 및 역할 체계

### 3.1 다중 소속 구조 (핵심)

선생님은 **여러 학원에 소속**될 수 있고, 학생은 **학원 레슨 + 개인 레슨을 병행**할 수 있습니다.

#### 현실 시나리오

```
[선생님 A]
    │
    ├── OO음악학원 소속 (강사)
    │   └── 학생 1, 2, 3 (학원 수강생)
    │
    ├── XX피아노학원 소속 (강사)
    │   └── 학생 4, 5 (학원 수강생)
    │
    └── 개인 레슨
        └── 학생 6, 7 (개인 수강생)


[학생 B]
    │
    ├── OO음악학원에서 바이올린 레슨 (선생님 A)
    │   └── 8회권 수강권
    │
    └── 개인적으로 피아노 레슨 (선생님 C) ← 학원과 무관
        └── 월정액 수강권
```

#### 관계 모델

```
기존 (1:1 관계):
Teacher ─── Student

변경 (N:M 관계 + Context):
Teacher ──┬── Membership ──── Organization (학원)
          │
          └── TeacherStudentRelation ── Student
                    │
                    ├── organizationId (nullable: null이면 개인)
                    ├── subscriptionId (연결된 수강권)
                    └── instrument (악기)
```

### 3.2 계정 타입

### 3.3 학원 역할 체계 (3단계)

| 역할 | 설명 | 주요 권한 |
|------|------|----------|
| **대표 (Owner)** | 학원 개설자, 최고 관리자 | 모든 권한, 학원 설정, 역할 변경 |
| **매니저 (Manager)** | 운영 담당자 | 학생 배정, 수강권 발행, 매출 조회 |
| **강사 (Instructor)** | 레슨 담당 강사 | 배정된 학생만 관리, 레슨 기록 |

## 4. 데이터 소유권 정책

### 4.1 기본 원칙: 3자 공동 소유

레슨 기록은 **학원/선생님**, **학생** 모두에게 소유권이 있습니다.
학생은 비용을 지불하고 받은 레슨이므로, 선생님이 탈퇴해도 본인 기록을 계속 열람할 수 있습니다.

```
┌─────────────────────────────────────────────────────────────┐
│                    데이터 소유권 구조 (3자)                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│      [학원/선생님]                    [학생/학부모]           │
│           │                              │                  │
│           │         공동 소유            │                  │
│           └────────────┬─────────────────┘                  │
│                        │                                    │
│                   [레슨 기록]                                │
│                        │                                    │
│           ┌────────────┼────────────┐                       │
│           ▼            ▼            ▼                       │
│      선생님 탈퇴    학생 탈퇴    선생님 변경                   │
│      → 학생 계속    → 선생님    → 새 선생님은                 │
│         열람 가능     보관 유지     학생 승인 필요             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 레슨 기록 공개 범위 (3단계)

학생이 자신의 레슨 기록 공개 범위를 설정할 수 있습니다.

| 공개 레벨 | 아이콘 | 설명 | 열람 가능자 |
|----------|:------:|------|------------|
| **전체 공개** | 🌐 | 누구나 열람 가능 | 모든 사용자 |
| **현재 선생님만** | 👤 | 담당 선생님만 열람 | 현재 담당 선생님 |
| **비공개** | 🔒 | 본인만 열람 | 학생/학부모만 |

### 4.3 데이터 유형별 기본 공개 설정

| 데이터 유형 | 기본값 | 변경 가능 | 설명 |
|------------|--------|:--------:|------|
| **레슨 노트** | 👤 현재 선생님 | ✅ | 학습 내용 |
| **레퍼토리 목록** | 🌐 전체 공개 | ✅ | 포트폴리오 성격 |
| **녹음 파일** | 🔒 비공개 | ✅ | 개인 연습 민감 |
| **연습 기록** | 👤 현재 선생님 | ✅ | 과제 확인 |
| **연락처** | 🔒 비공개 | ❌ | 개인정보 (변경 불가) |
| **결제 정보** | 🔒 비공개 | ❌ | 개인정보 (변경 불가) |

### 5.1 수강권 유형 (혼합형 통합)

> 변경일: 2026-01-25
> 배경: 월정액도 실제로는 "월 4회" 등 횟수 개념이 있음. 기간 + 횟수 동시 표시로 통합.

#### 기본 유형

| 유형 | 설명 | 미사용분 | 기간 표시 | 횟수 표시 |
|------|------|:-------:|:--------:|:--------:|
| **체험** (Trial) | 1회 체험 레슨 | - | - | 1회 |
| **월정액** (Monthly) | 월 단위 정기 (월 N회 포함) | ❌ **소멸** | ✅ D-N | ✅ N/M회 |
| **회차권** (Package) | N회권 (유효기간 있음) | ✅ **이월** | ✅ D-N | ✅ N/M회 |

#### ⚠️ 월정액 vs 회차권 핵심 차이

| 구분 | 월정액 | 회차권 |
|------|--------|--------|
| **미사용분** | ❌ **소멸** (다음달 이월 불가) | ✅ **이월** (유효기간 내) |
| **리셋** | ✅ 매월 초 `usedLessons = 0` | ❌ 누적 |
| **5주차 정책** | ✅ 해당 | ❌ 해당 없음 |
| **회당 단가** | 상대적으로 저렴 | 상대적으로 비쌈 |
| **적합 대상** | 규칙적 수강 가능자 | 불규칙 일정 보유자 |

#### 시나리오 비교

**월정액 (4회/월, 20만원)**
```
1월: 4회 중 3회만 사용 → 1회 소멸 ❌
2월: 새로 4회 시작 (이월 없음)
     usedLessons = 0 리셋
```

**회차권 (8회, 38만원)**
```
1월: 3회 사용 → 5회 남음
2월: 남은 5회 계속 사용 가능 ✅
     usedLessons = 3 유지
```

#### 혼합형 UI 표시

모든 수강권은 "기간 + 횟수" 동시 표시:

#### 🆕 결제 방식 (BillingType)

```dart
/// 결제 방식 (선생님/학원 설정용)
enum BillingType {
  perPackage,   // 회차 결제 (수업 시작 전 N회분 결제)
  monthly,      // 월정액 결제 (매월 고정일 결제)
}
```

| 결제 방식 | 결제 시점 | 결제 주기 | 5주차 정책 |
|----------|----------|----------|:----------:|
| `perPackage` | 수업 시작 전 | 불규칙 (4주마다) | ❌ 해당 없음 |
| `monthly` | 매월 N일 | 규칙적 | ✅ 적용 |

#### 🆕 보너스 수강권 (bonusCount)

5주차 보너스, 이벤트, 추천 등으로 추가 지급되는 횟수

```dart
/// 잔여 횟수 계산 (학생에게 표시)
int get remainingLessons {
  final base = type == SubscriptionType.monthly
      ? lessonsPerMonth
      : totalLessons;
  return (base ?? 0) + bonusCount - usedLessons;
}
```

**학생에게 표시:**
```
수강권 5회 남음
├── 기본: 4회
├── 보너스: +1회 (5주차)
└── 사용: 0회
```

#### 월정액 리셋 정책

| 시점 | 동작 | 설명 |
|------|------|------|
| 매월 1일 00:00 | `usedLessons = 0` | 기본 정책 |
| 또는 수강 시작일 기준 | 시작일 + N개월 | 15일 시작 → 매월 15일 리셋 |

> ⚠️ **주의**: 미사용분 소멸 전 알림 발송 필요 (D-3, D-1)

#### 5주차 정책 연동 (월정액만)

월정액에서 한 달에 5주가 있는 경우 → **5주차 정책** 적용

→ 상세: [lesson_schedule.md](../lesson/lesson_schedule.md#5주차-정책-월-4회-기준-정기레슨)

| 정책 | 설명 | 학생에게 표시 | 결제 |
|------|------|-------------|------|
| **skip** (기본) | 5주차 자동 휴강 | "7/29 휴강" | 4회 고정 |
| **bonus** | 🆕 보너스 수강권 지급 | "🎁 보너스 +1회" | 4회 고정 |
| **deduct** | 기존 수강권에서 차감 | "수강권 -1회 차감" | 4회 고정 |
| **optional** | 학생 선택 | "5주차 수업 선택" | 4회 + 선택시 |

> **권장**: `bonus` 정책 - 학생 만족도 높고, "보너스 수강권" 표시로 명확함

#### 🆕 실제 학원 결제 패턴 비교

> 추가일: 2026-01-25
> 출처: 실제 보컬/음악학원 운영 사례

##### Pattern 1: 회차권 방식 (수업 시작일 기준 결제)

```
[첫 수업일] → [4주분 결제] → [4주 수업] → [다시 결제] → ...

예시 타임라인:
├── 1/5 결제 (4회분) → 1/5, 1/12, 1/19, 1/26 수업
├── 2/2 결제 (4회분) → 2/2, 2/9, 2/16, 2/23 수업
├── 3/2 결제 (4회분) → 3/2, 3/9, 3/16, 3/23 수업
└── ...
```

| 장점 | 단점 |
|------|------|
| 수업 시작 전 결제로 단순함 | ❌ 결제일이 매달 다름 |
| 유연한 일정 조정 가능 | ❌ 5주차 월에 두 번 결제 가능 |
| 단기 수강에 적합 | 결제 관리 복잡 |

**5주차 문제:**
```
5주가 있는 달 (예: 7월, 화요일 5회)
├── 7/1 (1회) ← 이전 결제분
├── 7/8 (2회)
├── 7/15 (3회)
├── 7/22 (4회) ← 이전 결제분 소진
├── 7/29 ❓ ← 새로 결제 필요 (한 달에 두 번 결제)
```

##### Pattern 2: 월정액 방식 (고정 결제일)

```
[매월 N일 결제] → [그 달 수업 진행 (4주든 5주든)]

예시 타임라인 (결제일: 매월 27일):
├── 1/27 결제 → 2월 수업 (4회 또는 5회)
├── 2/27 결제 → 3월 수업 (4회 또는 5회)
├── 3/27 결제 → 4월 수업 (4회 또는 5회)
└── ...
```

| 장점 | 단점 |
|------|------|
| ✅ 결제일 고정 (예측 가능) | 중간 해지 시 정산 필요 |
| ✅ 5주차는 보너스/정책으로 처리 | 장기 수강 전제 |
| 결제 관리 간편 | - |

**5주차 처리:**
```
5주가 있는 달 (예: 7월, 화요일 5회)
├── 7/1 (1회)
├── 7/8 (2회)
├── 7/15 (3회)
├── 7/22 (4회)
├── 7/29 (5회) ← 보너스 수업 (always 정책)
└── 결제는 1회만 (월정액)
```

##### 패턴 비교 요약

| 구분 | 회차권 (Pattern 1) | 월정액 (Pattern 2) |
|------|-------------------|-------------------|
| **결제 시점** | 수업 시작일 기준 | 매월 고정일 (예: 27일) |
| **결제 주기** | 불규칙 (4주마다) | 규칙적 (매월) |
| **5주차 처리** | 추가 결제 필요 | 보너스 또는 휴강 |
| **결제 횟수/년** | 13회 (52주÷4) | 12회 |
| **적합 대상** | 단기/유동 일정 | 장기/정기 수강 |
| **학원 선호도** | 개인 레슨 | 학원 정규반 |

### 5.1.1 부가 서비스 옵션 (학원)

> 추가일: 2026-01-25

```dart
/// 수강권 부가 서비스 옵션
class SubscriptionOption {
  final String id;
  final SubscriptionOptionType type;    // practice_room, instrument_rental, ...
  final SubscriptionLimitType limitType; // unlimited, count, hours
  final int? limitValue;                 // 횟수 또는 시간 (unlimited면 null)
  final int usedValue;                   // 사용량
  final String? description;             // 추가 설명
}

enum SubscriptionOptionType {
  practiceRoom,      // 연습실
  instrumentRental,  // 악기 대여
  recordingStudio,   // 녹음실
  ensembleRoom,      // 합주실
  other,             // 기타
}

enum SubscriptionLimitType {
  unlimited,  // 무제한
  count,      // 횟수제
  hours,      // 시간제
}
```

### 5.1.2 교차 수강권 (학원)

> 추가일: 2026-01-25
> 참고 사례: 뮤라벨(Music Life Balance) - 성인 전문 음악학원

#### 개요

하나의 수강권으로 여러 악기/클래스를 자유롭게 수강할 수 있는 모델입니다.

| 특징 | 설명 | 예시 |
|------|------|------|
| **교차 수강** | 1개 수강권으로 여러 악기 수강 | 피아노, 바이올린, 첼로, 보컬 |
| **셀프 예약** | 앱으로 원하는 시간에 레슨 신청 | 예약 시스템 연동 |
| **연습실 포함** | 레슨권 보유 시 연습실 이용 | 무제한 or 횟수제 |
| **가격** | 회차권 기반 | 4회 25만원, 8회 44만원 |

#### 기존 모델 vs 교차 수강 모델

```
[기존 모델] 수강권 → 클래스 (1:1 고정)
┌────────────────┐     ┌──────────────┐
│ 바이올린 8회권  │ ──▶ │ 바이올린 클래스 │
└────────────────┘     └──────────────┘
  ❌ 피아노에 사용 불가

[교차 수강 모델] 수강권 → 학원 전체
┌────────────────┐     ┌──────────────┐
│ 뮤라벨 8회권   │ ──▶ │ 피아노 클래스  │
│ (교차 수강)    │ ──▶ │ 바이올린 클래스 │
└────────────────┘ ──▶ │ 첼로 클래스    │
                   ──▶ │ 보컬 클래스    │
                       └──────────────┘
  ✅ 모든 클래스에서 자유롭게 사용
```

#### 수강권 범위 (SubscriptionScope)

| 범위 | 코드 | 설명 | 사용 예시 |
|------|------|------|----------|
| **단일 클래스** | `singleClass` | 지정 클래스에서만 사용 | 기존 방식 (기본값) |
| **복수 클래스** | `multiClass` | 지정한 클래스들에서만 사용 | 피아노+바이올린만 허용 |
| **학원 전체** | `organization` | 학원 내 모든 클래스 사용 | 뮤라벨 교차 수강권 |

#### 데이터 구조

```dart
/// 수강권 사용 범위
enum SubscriptionScope {
  singleClass,    // 단일 클래스 (기존 방식)
  multiClass,     // 복수 클래스 지정
  organization,   // 학원 전체
}

/// Subscription 확장 필드
class Subscription {
  // 기존 필드
  final String membershipId;          // 기본 소속 (필수)

  // 🆕 교차 수강 지원 필드
  final SubscriptionScope scope;      // 사용 범위 (기본: singleClass)
  final String? organizationId;       // 학원 ID (scope=organization)
  final List<String>? allowedClassIds; // 허용 클래스 목록 (scope=multiClass)

  // 기존 필드들...
}

/// 수강권 사용 기록 (교차 수강 시 어떤 클래스에서 사용했는지)
class SubscriptionUsage {
  final String id;
  final String subscriptionId;   // 수강권 ID
  final String classId;          // 사용한 클래스
  final String? lessonId;        // 연결된 레슨 ID
  final DateTime usedAt;         // 사용 일시
}
```

### 5.4.1 🆕 대량 구매 할인/보너스 정책

> 추가일: 2026-01-25

학원/선생님이 회차권 대량 구매 시 할인율 또는 무료 횟수를 설정할 수 있습니다.

#### 정책 유형

| 유형 | 설명 | 예시 |
|------|------|------|
| **할인율** (discount) | 금액에서 N% 할인 | 10회권 10% 할인 → 450,000원 |
| **보너스 횟수** (bonusLessons) | 무료 N회 추가 | 10회권 구매 시 +1회 무료 |

#### 설정 예시

```dart
/// 대량 구매 할인/보너스 정책
class PackageDiscountPolicy {
  final int minLessons;        // 최소 구매 횟수 (예: 8)
  final DiscountType type;     // discount 또는 bonusLessons
  final int value;             // 할인율(%) 또는 보너스 횟수
}

enum DiscountType {
  discount,      // 할인율 (%)
  bonusLessons,  // 보너스 횟수
}
```

### 5.6 외부 결제 관리 (계좌이체/현금)

우리 시스템은 **결제가 외부**에서 이루어지므로, 결제 기록만 관리합니다.

#### 타사 서비스 결제 처리 방식 비교

| 방식 | 설명 | 예시 서비스 |
|------|------|------------|
| **PG 연동형** | 앱 내 카드/간편결제 → 자동 수납 | 결제선생, 스튜디오메이트 |
| **결제 기록형** | 외부 결제 후 수동 "결제 확인" | 대부분의 학원 관리 시스템 |
| **청구서형** | 청구서 발송 후 결제 확인 대기 | 결제선생 알림톡 |

#### 우리 시스템의 결제 처리 흐름


#### 결제 방법별 처리

| 결제 방법 | 처리 방식 | Payment.method |
|-----------|----------|----------------|
| 카드 (외부) | 매니저가 수동 확인 후 기록 | `card` |
| 계좌이체 | 입금 확인 후 "결제 확인" 처리 | `transfer` |
| 현금 | 수령 후 "결제 확인" 처리 | `cash` |
| 미수금 | 수강권 먼저 발행, 나중에 결제 확인 | - |

#### 가족(자녀 2명 이상) 수강권 시나리오

```
학부모 김OO
├── 자녀1: 김민수 (바이올린)
└── 자녀2: 김서연 (피아노)
```

**처리 플로우**:

| 단계 | 위치 | 담당자 | 작업 |
|------|------|--------|------|
| 1 | 외부 | 학부모 | 40만원 계좌이체 (20만원 × 2명) |
| 2 | **웹** | 학원 매니저 | 입금 확인 |
| 3 | **웹** | 학원 매니저 | Payment 1건 생성 (40만원, transfer) |
| 4 | **웹** | 학원 매니저 | 김민수 Subscription 발행 (20만원) |
| 5 | **웹** | 학원 매니저 | 김서연 Subscription 발행 (20만원) |
| 6 | **앱** | 학부모 | 자녀들 수강권 현황 조회 |
| 7 | **앱** | 선생님 | 레슨 시 해당 학생 수강권 차감 |

- 수강권은 **학생별** 발급 (Subscription.studentId)
- Payment는 **통합 결제 기록**으로 사용 가능
- 여러 Subscription이 하나의 Payment를 참조할 수 있음

```dart

Subscription {
  studentId: "김민수",
  paymentId: "pay_001",     // 동일한 Payment 참조
  amount: 200000,
}

// Subscription #2 - 김서연
```

### 5.8 레슨 예약 방식: 정기레슨 vs 회차권

> 결정일: 2026-01-25

#### 핵심 차이

| 구분 | 정기레슨 (월정액) | 회차권 (패키지) |
|------|-----------------|----------------|
| **레슨 일정** | ✅ 고정 (매주 같은 요일/시간) | 🔄 유동 (매번 협의) |
| **예약 주체** | 초기 설정 후 자동 | 선생님 제안 → 학생 선택 |
| **스케줄 관리** | 최소 (변경 요청만) | 매 레슨 예약 필요 |
| **결제 확인** | 월초 스케줄 생성 + 결제 알림 | 수강권 구매 시 |
| **미입금 처리** | ⚠️ 경고 표시 (레슨 가능) | - |
| **적합 대상** | 장기/정기 수강생 | 불규칙 일정 수강생 |
| **billingType** | `monthly` | `perPackage` |

#### 환불 정책 원칙

```
1. "법정 환불 기준 준수" ⚖️
   - 학원법 시행령 별표4 (교습비 반환기준) 적용
   - 공정거래위원회 표준약관 참고 (위약금 최대 10%)

2. "5일 이내 환불 처리" ⏰
   - 학원법 시행령 제18조제3항에 따라 법정 의무
   - 환불 요청일 기준 5영업일 이내 입금 완료

3. "실제 결제금액 기준"
   - 정가가 아닌 할인 적용된 실제 결제금액 기준
   - 보너스 횟수는 환불 계산에서 제외

4. "기록 보존"
   - 환불 이력은 영구 보존
   - 원본 수강권 정보 유지 (soft delete)
```

#### 환불 계산 공식

**1. 회차권 (Package)**

```
환불금액 = 결제금액 × (잔여횟수 / 기본횟수) - 위약금

- 잔여횟수: remainingLessons - bonusCount (보너스 제외)
- 기본횟수: totalLessons (보너스 미포함)
- 위약금: 환불금액의 최대 10% (단순 변심 시)
```

| 사용률 | 환불액 | 위약금 |
|--------|--------|--------|
| 미사용 | 100% | 10% |
| 1/3 미만 | 2/3 | 10% |
| 1/2 미만 | 1/2 | 10% |
| 1/2 이상 | 환불 불가 | - |

**2. 월정액 (Monthly)**

```
환불금액 = 결제금액 × (잔여일수 / 총일수) - 위약금

- 잔여일수: endDate - 환불요청일
- 총일수: endDate - startDate
- 사용한 레슨 횟수도 차감 가능 (선택적)
```

| 경과 | 환불액 |
|------|--------|
| 1/3 경과 전 | 2/3 환불 |
| 1/2 경과 전 | 1/2 환불 |
| 1/2 경과 후 | 환불 불가 |

**3. 체험 (Trial)**

```
- 미사용: 전액 환불
- 사용 후: 환불 불가
```

#### 위약금 면제 사유

| 사유 | 위약금 | 비고 |
|------|--------|------|
| 선생님 사정 (퇴사, 부상 등) | 면제 | 전액 환불 |
| 학원 폐업 | 면제 | 전액 환불 |

| 질병 (진단서 필요) | 면제 | 잔여분 환불 |
| 단순 변심 | 10% | 법정 최대치 |

```dart
class RefundCalculator {
  /// 환불금액 계산
  RefundCalculation calculate({
    required Subscription subscription,
    required RefundReason reason,
    required DateTime requestDate,
  }) {
    final isPackage = subscription.type == SubscriptionType.package;

    // 보너스 제외한 잔여 횟수
    final baseRemaining = isPackage
        ? (subscription.totalLessons! - subscription.usedLessons)
        : (subscription.lessonsPerMonth! - subscription.usedLessons);
    final remainingWithoutBonus = baseRemaining.clamp(0, baseRemaining);

    // 기본 횟수
    final baseTotal = isPackage
        ? subscription.totalLessons!
        : subscription.lessonsPerMonth!;

    // 사용률 계산
    final usageRate = subscription.usedLessons / baseTotal;

    // 환불 가능 여부
    if (usageRate >= 0.5) {
      return RefundCalculation(
        isRefundable: false,
        reason: '1/2 이상 사용하여 환불이 불가합니다.',
      );
    }

    // 환불금액 계산
    final refundRate = remainingWithoutBonus / baseTotal;
    var refundAmount = (subscription.amount * refundRate).round();

    // 위약금 계산 (단순 변심만)
    var penaltyAmount = 0;
    if (reason == RefundReason.customerRequest) {
      penaltyAmount = (refundAmount * 0.1).round(); // 10%
      refundAmount -= penaltyAmount;
    }

    return RefundCalculation(
      isRefundable: true,
      originalAmount: subscription.amount,
      usedLessons: subscription.usedLessons,
      remainingLessons: remainingWithoutBonus,
      refundAmount: refundAmount,
      penaltyAmount: penaltyAmount,
      penaltyWaived: reason != RefundReason.customerRequest,
    );
  }
}
```

### 6.3 강사 정산 참고 자료

앱은 강사 정산을 직접 처리하지 않지만, 참고용 통계 제공:

```dart
/// 강사 레슨 통계 (조회용)
class InstructorLessonStats {
  final String instructorId;
  final int totalLessons;        // 총 레슨 수
  final int packageLessons;      // 패키지 레슨 수
  final int monthlyLessons;      // 월정액 레슨 수
  final int trialLessons;        // 체험 레슨 수
  final DateTime periodStart;
  final DateTime periodEnd;

  // 정산 금액은 학원에서 계산 (앱은 기록만)
}
```

### 6.4 왜 정산을 앱에서 안 하는가?

| 이유 | 설명 |
|------|------|
| **법적 복잡도** | PG 연동 시 전자금융업 등록 필요 가능성 |
| **CS 부담** | 정산 분쟁 발생 시 중재 역할 부담 |
| **업계 관행** | 학원-강사 정산은 계약에 따라 다양 (5:5, 6:4 등) |
| **개발 복잡도** | PG 연동, 정산 시스템 개발 비용 |

> **참고**: 바디코디, My Music Staff도 **계산 기능만 제공**하고 실제 지급은 외부 처리

## 8. 데이터 모델

> **📌 엔티티 참조 안내**
>
> 핵심 엔티티 정의는 [student_class_system.md](../student/student_class_system.md)를 **Single Source of Truth**로 참조하세요:
> - LessonClass, ClassMembership, Student, LessonLocation, Subscription
>
> 이 문서에는 학원 전용 엔티티(Organization, Membership 등)만 정의합니다.

### 8.1 Organization (학원)

**조직 유형 (OrganizationType)**
| 값 | 설명 |
|----|------|
| `academy` | 학원 (사업자) |
| `studio` | 개인 스튜디오 |

**주요 필드**
- `name`, `ownerId`: 학원 기본 정보
- `businessNumber`: 사업자등록번호 (선택)
- `settings`: 학원 설정 (패키지 옵션, 취소 정책 등)

**학원 설정 (OrganizationSettings)**
- `packageOptions`: 패키지 옵션 목록
- `requireParentConsent`: 미성년자 학부모 동의 필수
- `lessonCancelHours`: 레슨 취소 가능 시간
- `requireSubscription`: 수강권 필수 (학원 = true)

### 8.2 Membership (학원-강사 관계) - 다중 소속 지원

선생님은 **여러 학원에 소속**될 수 있습니다.

**역할 (MemberRole)**
| 값 | 권한 |
|----|------|
| `owner` | 대표: 모든 권한 |
| `manager` | 매니저: 학생 배정, 수강권 발행 |
| `instructor` | 강사: 배정된 학생만 |

**상태 (MemberStatus)**
| 값 | 설명 |
|----|------|
| `active` | 활성 |
| `inactive` | 비활성 (일시 중지) |
| `terminated` | 퇴사 |

**퇴사 사유 (TerminationReason)**
- `resignation`: 자진 퇴사
- `dismissal`: 해고
- `contractEnd`: 계약 종료

**다중 소속 예시**
```
선생님 A:
├── Membership { organizationId: "OO음악학원", role: instructor }
└── Membership { organizationId: "XX피아노학원", role: instructor }
```

### 8.3 TeacherStudentRelation (선생님-학생 관계) - Context 포함

학생은 **학원 레슨 + 개인 레슨을 병행**할 수 있습니다.

**핵심 설계**: `organizationId`가 null이면 개인 레슨

**상태 (RelationStatus)**
| 값 | 설명 |
|----|------|
| `active` | 활성 (레슨 진행 중) |
| `paused` | 일시 중지 |
| `ended` | 종료 |

**주요 필드**
- `teacherId`, `studentId`: 관계 연결
- `organizationId`: 학원 ID (null = 개인 레슨)
- `subscriptionId`: 연결된 수강권
- `instrument`: 악기

**병행 레슨 예시**
```
학생 B:
├── 선생님A / OO음악학원 / 바이올린
└── 선생님C / 개인 (null) / 피아노
```

### 8.4 Subscription (수강권)

> **📌 참조**: 기본 Subscription 엔티티는 [subscription.md](../../schema/entities/subscription.md) 참조

**학원 모드 확장 필드**
- `organizationId`: 학원 ID (null = 개인)
- `issuerId`: 발행자 (대표/매니저/선생님)
- 정지 관련: `isSuspended`, `suspendedAt`, `suspendedUntil`, `suspendReason`

**확장된 상태 (학원 모드)**
| 값 | 설명 |
|----|------|
| `pending` | 결제 대기 |
| `active` | 활성 |
| `expired` | 만료 (유효기간) |
| `exhausted` | 소진 (횟수) |
| `suspended` | 정지 |
| `cancelled` | 취소 |

### 8.5 SubscriptionUsage (수강권 사용 기록)

**주요 필드**
- `subscriptionId`, `lessonId`: 수강권-레슨 연결
- `instructorId`: 레슨 진행 강사
- `deductedCount`: 차감 횟수 (보통 1)
- `remainingAfter`: 차감 후 잔여

### 8.6 RecordVisibility (레슨 기록 공개 설정)

**공개 범위 (VisibilityLevel)**
| 값 | 아이콘 | 설명 |
|----|:-----:|------|
| `public` | 🌐 | 전체 공개 |
| `currentTeacher` | 👤 | 현재 선생님만 |
| `private` | 🔒 | 비공개 (본인만) |

**공유 범위 (ShareScope)**
| 값 | 설명 |
|----|------|
| `all` | 전체 공유 |
| `recentSixMonths` | 최근 6개월 |
| `none` | 공유 안 함 |

**승인 상태 (ApprovalStatus)**
- `pending`, `approved`, `rejected`, `expired`

**RecordVisibilitySettings 필드**
- `defaultVisibility`: 기본 공개 범위
- 유형별 설정: `lessonNotes`, `repertoire`, `recordings`, `practiceRecords`
- 항상 비공개: 연락처, 결제 정보

### 13.2 학원 결제 서비스 비교 분석

#### 결제선생 (페이민트)

| 항목 | 내용 |
|------|------|
| **서비스 유형** | 비대면 모바일 청구서 결제 |
| **운영사** | 페이민트 |
| **금융위 지정** | 2019년 혁신금융서비스 |
| **가맹점 수** | 101,700개 (2025년 4분기) |
| **월 거래액** | 3,300억원 |
| **누적 거래액** | 8.8조원 |

**수수료 구조**:
| 항목 | 금액 |
|------|------|
| 가입비 | 없음 |
| 월정액 | 없음 |
| 약정기간 | 없음 |
| 카드 수수료 | 약 0.4%~0.8% (카드사 직접 정산) |
| 메시지 발송 | 건당 50원 |
| 신규 카드가맹 대행 | 30,000원 (미가맹 시) |

**주요 특징**:
- PG사 거치지 않고 카드사 직접 정산 → 수수료 절감
- 학원비 제휴 할인 적용 가능 (학부모 카드 혜택)
- 면세 처리 지원
- 12개 간편결제 지원 (9개 카드앱 + 3개 페이앱)
- PC 대량 청구서 발송 가능
- 1~3일 빠른 정산

**적합 대상**: 비대면 청구서 결제가 필요한 소규모 학원

#### 에듀클릭 (페이소프트)

| 항목 | 내용 |
|------|------|
| **서비스 유형** | 학원관리 + CMS 자동이체 + 카드정기결제 통합 |
| **운영사** | (주)페이소프트 |
| **연동 은행** | 24개 시중 은행 |
| **연동 카드사** | 전 카드사 |
| **도입 기업** | 4만 5천 곳 |

**요금제**:
| 요금제 | 설명 |
|--------|------|
| BASIC | 학생관리 + 청구서 비대면 결제 |
| BUSINESS | 은행 자동이체 + 카드 정기결제 연동 |

**주요 기능**:
- 학생 상담관리, 일정관리
- 은행 자동이체 (CMS)
- 카드 정기결제
- 비정기 결제 (교재비, 특강비)
- 출결 관리 (QR코드, 출결번호)
- SMS, 카카오 알림톡 발송
- 현금영수증 자동 발행

**적합 대상**: 학원관리 + 결제를 통합하려는 중대형 학원

#### CMS 자동이체 일반 정보

## 부록: 스튜디오메이트 이용약관 분석

### A.1 주요 조항 분석

| 항목 | 스튜디오메이트 규정 | lesson-app 적용 |
|------|-------------------|----------------|

| **강사 퇴사** | 명시적 규정 없음 | 명확한 퇴사 처리 플로우 정의 |
| **레슨 기록 저작권** (제27조 8항) | 탈퇴 후 회사가 보존/활용 가능 | 학원 보관 + 강사 내보내기 허용 |
| **정산** | 명시적 규정 없음 (시설 간 거래 책임 없음) | 기록만 (정산 리포트 제공) |
| **회원 탈퇴 시 데이터** (제9조, 제20조) | 개인정보 30일 보유 후 삭제, 법정 보관 5년 | 동일 적용 |

### A.2 스튜디오메이트 제27조 8항 (중요)

> "회원탈퇴를 한 경우에는 본인이 기록한 저작물 일체가 **삭제되지 않은 채 보존**되며
> 회사 내부 규정에 맞게 재구성하여 **사용될 수 있습니다**"

**시사점**: 강사가 작성한 레슨일지도 퇴사 후 회사(학원)가 보존·활용 가능

### A.3 lesson-app 차별화 포인트

| 구분 | 스튜디오메이트 | lesson-app |
|------|--------------|------------|
| 강사 퇴사 규정 | 없음 | ✅ 명확한 처리 플로우 |
| 강사 내보내기 | 없음 | ✅ PDF + JSON 제공 |
| 연락처 보호 | 언급 없음 | ✅ 내보내기 시 연락처 제외 |
