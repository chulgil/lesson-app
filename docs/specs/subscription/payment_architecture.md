## 1. 핵심 원칙

> **선생님/학원 수강료는 앱 밖에서, 앱은 수강권 상태만 기록한다.**

Lessonaza 의 입금/과금 정책은 흐름의 주체로 결정한다:

| 흐름 | 돈을 받는 주체 | 현행 정책 | 앱의 역할 |
|------|----------------|-----------|-----------|
| **A. 선생님 ↔ 학생/학부모** | 선생님 | **무통장입금 / 현금 등 외부 입금** | 수강권 제안, 입금 안내, 입금 완료 알림, 입금 상태 기록 |
| **A'. 학원 ↔ 학생/학부모** | 학원 | **무통장입금 / 현금 등 외부 입금** | 학원 수강권 입금 상태 기록 |
| **B. 앱관리자 → 사용자** | Lessonaza | **✅ 구현됨 — 앱 내 결제(IAP), 2026-06-03 코드 검증** | 앱 사용료 과금, 유료 플랜(Pro/Studio/Lifetime), 프리미엄 기능 결제 |

**흐름 A/A'(수강료)는 변함없이 무통장입금만이다.** 선생님이나 학원이 학생/학부모에게 받는 수강료에 대해 Lessonaza는 PG, 카드 결제, 간편결제, 정산, 영수증 발행, 에스크로를 **제공하지 않는다** (정책 유지, 2026-06-03 코드 검증 — `features/auth/.../terms_agreement_section.dart`에 "회사는 결제 대행 서비스를 제공하지 않습니다. 수강료 결제는 선생님과 학생/학부모 간에 직접" 명시).

**흐름 B(앱 사용료)는 이제 구현되었다 (2026-06-03 갱신).** Apple StoreKit / Google Play Billing 기반 **인앱결제(IAP)** 로 구현되며, 이는 PG(결제대행)가 아니라 스토어 결제다. 수강료(A/A')와 데이터·로직상 절대 섞이지 않는다. 상세 SSOT는 [paywall_spec.md](./paywall_spec.md), 코드는 `features/billing/`(`iap_service.dart`, `domain/services/billing_guard.dart`, `app_billing_provider.dart`) 참조. (구 "흐름 B 미구현" 표기 정정 — §3.2 참고)

## 2. 현행 정책 — 수강료 무통장입금

### 2.1 사용자 경험

```
선생님/학원 → 수강권 제안
학생/학부모 → 외부 은행 앱 또는 현금으로 입금
학생/학부모 → Lessonaza에서 "입금 완료 알림" 전송
선생님/학원 → 실제 통장 확인 후 수강권 발급/확정
```

### 2.2 허용 범위

| 항목 | 정책 |
|------|------|
| 입금 수단 | 외부 무통장입금, 현금 등 앱 밖 입금 |
| 학생/학부모 액션 | 입금 완료 알림, 제안 수락/거절 |
| 선생님/학원 액션 | 실제 입금 확인 후 수강권 발급/확정 |
| 앱 기록 | `Subscription`, `SubscriptionProposal`, `payment_confirmed`, `payment_status` 등 수강권 흐름에 필요한 상태 |
| 자동화 | 없음. 입금 매칭, 자동 청구, 자동 정산을 하지 않는다 |
| 환불 | 외부 송금으로 처리. 앱은 별도 환불 기능을 현행 스펙으로 정의하지 않는다 |

### 2.3 명시적 비범위

현재 스펙은 다음 기능을 정의하지 않는다:

- `/payments/*` 라우터
- `payment_service`
- 독립 결제 API
- 카드/간편결제/PG SDK
- PG webhook
- 카드 토큰화
- 자동 입금 매칭
- 앱 발행 영수증
- 정산/수수료/에스크로
- 선생님/학원 수강료에 대한 앱 중개 결제

기존 코드에 `Payment` 모델이 남아 있더라도 현행 API 구현 지시가 아니다. 수강권 흐름의 상태 기록 또는 레거시 모델로만 해석한다.

## 3. 미래 정책 — 앱관리자 사용료 과금

### 3.1 도입 조건

다음 시나리오가 확정될 때만 별도 결제 스펙을 작성한다:

| 시나리오 | 예시 |
|---------|------|
| 선생님 사용료 | 월 구독료, 학생 수 제한 해제, 분석 리포트 |
| 학생 프리미엄 | AI 피치, 녹음 비교, 클라우드 백업 |
| 학부모 플랜 | 자녀 통합 관리, 고급 알림 |
| 학원 플랜 | 강사/학생 수 기반 라이선스, 학원 통계 |

이 흐름은 **앱관리자(Lessonaza)가 사용자에게 직접 과금하는 B2C/SaaS 결제**다. 선생님이나 학원이 학생에게 받는 수강료와 섞지 않는다.

### 3.2 현행 구현 상태 (2026-06-03 갱신)

> 흐름 B IAP 구현으로 아래 다수 항목이 **이미 정의·구현**되었다. 상세 SSOT는 [paywall_spec.md](./paywall_spec.md).

| 항목 | 상태 |
|------|------|
| 요금제 (Free / Pro / Studio / Lifetime) | ✅ 정의됨 (`BillingPlan`) |
| 무료체험 (14일 Pro, 6번째 학생 트리거) | ✅ 구현 (`TrialActivationResult`, `BillingGuard`) |
| 인앱결제 적용 | ✅ IAP (StoreKit / Play Billing, `in_app_purchase ^3.2.0`) |
| 앱 사용료 결제 UI | ✅ Paywall(`FreeLimitSheet`) / Lifetime 프로모 배너 / 구독 배지 |
| IAP 영수증 검증 | ✅ FE 결선 (`/me/billing/iap/validate`), BE 미들웨어는 별도 |
| 환불 정책 | ⏸️ 스토어 정책에 위임 (앱 자체 환불 UI 없음) |
| 세금계산서 / 영수증 | ⏸️ 미정 (스토어 영수증으로 대체) |
| 관리자 매출 대시보드 | ⏸️ 미구현 |

> 참고 — 최초 작성 시점(2026-05) "미정"으로 두었던 원 목록: 요금제 / 무료체험 / 환불 정책 / PG 선택 / 인앱결제 적용 여부 / 세금계산서·영수증 정책 / 앱 사용료 결제 API / 앱 사용료 결제 UI / 관리자 매출 대시보드. PG는 흐름 B에도 **채택하지 않았고**(스토어 IAP로 대체) 흐름 A/A'에는 영구 비채택.

### 3.3 미래 구현 경계

미래 앱 사용료 결제가 확정되면 현행 수강권/입금 기록과 물리적으로 분리한다:

| 구분 | 현행 A/A' 수강료 | 미래 B 앱 사용료 |
|------|------------------|------------------|
| 돈을 받는 주체 | 선생님 / 학원 | Lessonaza 앱관리자 |
| 입금/결제 방식 | 앱 밖 무통장입금/현금 | 별도 스펙에서 결정 |
| 모델 | `Subscription`, `SubscriptionProposal` 중심 | `AppPayment`, `AppSubscription` 등 별도 모델 후보 |
| 라우터 | `/subscriptions/*` 중심 | `/billing/*` 등 별도 라우터 후보 |
| 서비스 | `subscription_service` 중심 | `billing_*` 서비스 후보 |

`/payments/*`를 현행 A/A' 수강료 API로 만들지 않는다. 미래 B 흐름도 스펙 확정 전에는 구현하지 않는다.
