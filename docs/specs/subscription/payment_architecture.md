## 1. 핵심 원칙

> **돈은 앱 밖에서, 기록은 앱 안에서.**

### 1.1 결제 흐름 분류 (2축)

Lessonaza 의 결제는 **흐름의 주체**가 누구인지로 정책이 결정된다:

| 결제 흐름 | 주체 | 정책 | 모듈 |
|----------|------|------|------|
| **A. 사용자 ↔ 사용자** (선생님 ↔ 학생/학부모) | 외부 | **무통장입금 영구** | PG 미채택 |
| **A'. 사용자 ↔ 사용자** (학원 ↔ 학생/학부모) | 외부 | **무통장입금 영구** | PG 미채택 |
| **B. 앱 → 사용자** (Lessonaza → 선생님/학부모/학생) | 앱 | 미정 (미래) | **PG 도입 트리거** |

**핵심**: 선생님이 학생에게 받는 수강료, 학원이 학생에게 받는 수강료는 **앱이 일체 개입하지 않으며 영구적으로 PG 미채택**. 앱이 PG 모듈을 도입하는 시점은 **앱 자체가 사용자에게 직접 과금**(SaaS 구독료, 프리미엄 기능 등)할 때뿐이다.

### 1.2 흐름 A / A' (사용자 ↔ 사용자) — 영구 정책

| 항목 | 정책 |
|------|------|
| PG 연동 | **영구 미채택** (Toss / Portone / 카카오페이 / 이니시스 등 없음) |
| 결제 수단 | **무통장입금 (계좌이체)** — 외부 은행 앱에서 직접 송금 |
| 확인 방식 | **수동 2단계** — 학생/학부모이 [입금완료] 클릭 → 선생님/학원이 통장 확인 후 [입금확인] |
| 자동화 | 입금 매칭 자동화 **없음** — 선생님/학원이 수동 대조 |
| 영수증 | 앱 발행 **없음** — 필요 시 선생님/학원이 외부에서 발행 |
| 환불 | 외부 송금 + 앱 상태 기록만 (`refunded`) |
| 학원 모드 | 1:1 레슨과 동일 정책 — 학원 ↔ 학생/학부모 직접 송금, 앱은 기록만 |

**근거**:
- 사제지간 / 학원-수강생 신뢰 관계 — 결제 중개 시 카드사 수수료 (2.5~3%) 부담을 누가 지느냐 갈등 발생
- 선생님 / 학원 자율성 우선 (계좌 / 정산 / 영수증 모두 선생님·학원 결정)
- 통신판매업 신고 / 전자상거래법 / 에스크로 의무 회피 — 앱이 결제 중개자가 되면 법적 책임 폭증
- **앱은 "기록 도구"이지 "결제 중개자"가 아니다**

### 1.3 흐름 B (앱 → 사용자) — 미래 PG 도입 트리거

다음 시나리오 발생 시에만 PG 모듈을 도입한다:

| 시나리오 | 예시 |
|---------|------|
| 선생님 SaaS 구독 | 월 X 원 — 학생 N명 이상 / 무제한 / 분석 리포트 등 |
| 학생 프리미엄 기능 | AI 피치 / 녹음 비교 / 클라우드 백업 등 유료 기능 |
| 학부모 가족 플랜 | 자녀 N명 통합 관리 / 알림 강화 등 |
| 학원 엔터프라이즈 | 학원 단위 라이선스, 강사 N명 / 학생 N명 / 통계 |

**중요**: 이는 **사용자 ↔ 사용자** 결제(흐름 A/A') 와 **완전히 다른 흐름**. 흐름 A 는 영구히 PG 미채택, 흐름 B 도입 시에도 흐름 A 는 그대로 무통장입금을 유지한다.

## 2. 현행 워크플로우 (PG 미채택)

### 2.1 데이터 흐름

```
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  학생 ──외부 은행 앱── 송금 ──▶ 선생님 계좌                  │
│   │                                  │                       │
│   │                                  │                       │
│   ▼                                  ▼                       │
│  Lessonaza 앱                 선생님 통장 알림 / 사본        │
│   │                                  │                       │
│   │ [입금완료] 클릭                  │ 수동 대조             │
│   │ (학생 자가 신고)                 │                       │
│   │                                  │                       │
│   ▼                                  ▼                       │
│  Payment.status =              Payment.status =              │
│  studentConfirmed         ─▶   confirmed                     │
│                                ─▶ Subscription 활성화         │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 상태 전환

```
pending (입금 대기)
    ├── [학생: 입금완료]    → studentConfirmed
    │       ├── [선생님: 입금확인] → confirmed (수강권 활성화)
    │       └── [선생님: 반려]     → pending
    ├── [납부기한 초과]    → overdue
    │       └── [입금 후]   → studentConfirmed
    ├── [취소]              → cancelled
    └── [환불 외부 송금]   → refunded (기록만)
```

### 2.3 백엔드 책임 (수동 워크플로우 only)

| API 카테고리 | 엔드포인트 | 역할 |
|-------------|-----------|------|
| 학생 액션 | `POST /payments/{id}/student-confirm` | 학생이 [입금완료] 클릭 |
| 선생님 액션 | `POST /payments/{id}/teacher-confirm` | 통장 확인 후 활성화 |
| 선생님 액션 | `POST /payments/{id}/teacher-reject` | 입금 미확인 반려 |
| 선생님 액션 | `POST /payments/{id}/refund` | 외부 송금 후 상태 기록 |
| 조회 | `GET /payments/overdue` | 미수금 목록 |
| 알림 | `POST /payments/{id}/remind` | 수동 입금 알림 (학생에게 푸시) |

### 2.4 백엔드 미보유 항목 (의도적 부재)

```
✗ NO PG SDK         (Toss / Portone / 카카오페이 등)
✗ NO webhook        (PG → 서버 콜백)
✗ NO 카드 토큰화    (PCI-DSS 범위 제외)
✗ NO 자동 매칭      (입금 내역 ↔ Payment 자동 연결)
✗ NO 영수증 발행    (NHN 영수증 / 국세청 등)
✗ NO 정산 시스템    (선생님 → 플랫폼 → 카드사 흐름)
✗ NO 에스크로       (앱이 돈을 보유하지 않음)
```

## 3. 미래 — 흐름 B (앱 → 사용자) PG 도입 시 신규 설계 요건 (Out of Scope)

> **중요**: 본 §3 은 **흐름 B (앱이 사용자에게 직접 과금)** 에만 적용된다.
> 흐름 A / A' (사용자 ↔ 사용자) 는 §1.2 의 정책에 따라 **영구 PG 미채택**.

### 3.1 1-Party SaaS 결제 흐름 (예상)

흐름 B 는 **3자 정산이 아닌 1자 결제 (B2C SaaS)** 다 — 앱이 사용자에게 직접 구독료/이용료를 받는다. 선생님 정산 / 에스크로 / 학원 매출 분배는 **본 흐름의 범위 밖** (흐름 A 영역).

```
┌───────────────────────────────────────────────────────────────┐
│                                                                │
│   사용자 (선생님 / 학부모 / 학생 / 학원)                       │
│       │                                                        │
│       │ ──── 카드 / 간편결제 ────▶  PG (Toss / Portone …)     │
│       │                                  │                     │
│       │                                  ▼                     │
│       │                         ┌────────────────┐             │
│       │                         │  Lessonaza 앱  │             │
│       │                         │  (B2C SaaS)    │             │
│       │                         └────────────────┘             │
│       │                                  │                     │
│       │     구독 활성화 / 기능 잠금 해제 ◀                     │
│       │                                                        │
│       │   환불: 정기 결제 해지 / 일할 환불 (앱 정책)           │
│                                                                │
└───────────────────────────────────────────────────────────────┘
```

**핵심 차이**:
- 에스크로 **없음** (앱이 자기 매출을 자기 계좌로 받음)
- 선생님 정산 **없음** (선생님은 본 흐름의 수신자가 아님)
- 플랫폼 수수료 **없음** (전액이 앱 매출)
- PG 수수료만 차감 (2.5~3%)

### 3.2 미정 항목 (PG 도입 결정 시 답해야 함)

| 항목 | 옵션 / 미정 사항 |
|------|------------------|
| 결제 모델 | 정기결제 (월/연 구독) / 단건결제 (프리미엄 기능 1회) / 혼합 |
| 무료체험 | N 일 무료 / 신용카드 등록 필수 여부 / 체험 종료 자동전환 |
| 환불 정책 | N 일 이내 무조건 환불 / 일할 환불 / 환불 불가 (디지털 콘텐츠) |
| 결제 실패 시 | 재시도 횟수 / 유예 기간 / 다운그레이드 시점 |
| 사업자 / 세금 | 부가세 포함/별도, 전자세금계산서 발행 의무 |
| PG 선택 | Toss / Portone / 카카오페이 / 이니시스 — 수수료 / 정기결제 지원 / UX 비교 |
| 결제 수단 | 카드 정기결제 / 간편결제 / 휴대폰 / 인앱결제 (App Store / Play Store) |
| 인앱결제 의무 | iOS / Android 디지털 콘텐츠 30% 수수료 강제 — 외부 결제 허용 여부 |
| 약관 / 법적 검토 | 전자상거래법 / 정기결제 자동갱신 고지 의무 / 청약철회 |

### 3.3 PG 도입 시 백엔드 추가 모듈 (예상 범위)

```
신규 모델:
  - subscriptions_app      (앱 SaaS 구독 — 기존 lesson subscription 과 다름)
  - subscription_plans     (요금제: free / pro / enterprise 등)
  - app_payments           (앱 결제 원장)
  - billing_keys           (정기결제 카드 빌링키 — 토큰 only, 카드번호 NO)
  - refund_records         (환불 이력)
  - pg_webhooks            (PG → 서버 콜백 로그)

신규 라우터:
  - /api/v1/billing/plans          (요금제 목록 / 변경)
  - /api/v1/billing/checkout       (PG SDK 토큰 발급, 빌링키 등록)
  - /api/v1/billing/subscriptions  (사용자 구독 상태 / 해지 / 재개)
  - /api/v1/billing/webhook        (PG → 서버, 서명 검증)
  - /api/v1/billing/refund         (환불 요청)

신규 서비스:
  - billing_gateway_service        (PG SDK 어댑터 — 정기결제 빌링키)
  - subscription_billing_service   (구독 상태 관리, 만료/갱신)
  - refund_service                 (환불 정책 적용)
  - reconciliation_service         (PG 원장 ↔ 앱 결제 대조)

기존 모델과 분리:
  - 기존 `Subscription` (수강권) 과 별도 테이블 (`AppSubscription`)
  - 기존 `Payment` (학생→선생님 무통장입금 기록) 과 별도 테이블 (`AppPayment`)
  - 흐름 A 와 흐름 B 의 데이터/로직을 **물리적으로 격리**
```

### 3.4 PG 도입 시 프론트엔드 추가 화면

```
사용자 공통:
  - 요금제 비교 / 선택 화면
  - 결제 진행 (PG SDK iframe / WebView)
  - 결제 완료 / 실패 처리
  - 결제 수단 관리 (카드 등록 / 변경 / 삭제)
  - 구독 관리 (현재 플랜 / 다음 결제일 / 해지)
  - 결제 내역 / 영수증 다운로드

앱 관리자 (신규 권한):
  - 매출 대시보드 (MRR / ARR / Churn)
  - 환불 승인 / 거절
  - 사용자 구독 상태 조회
  - PG 원장 대조
  - 요금제 / 프로모션 관리
```

### 3.5 흐름 A 와의 격리 원칙

PG 도입 시 흐름 B 의 코드/모델/라우터는 **흐름 A 와 물리적으로 분리**한다:

| 격리 대상 | 흐름 A (영구 무통장입금) | 흐름 B (PG SaaS) |
|----------|------------------------|------------------|
| 모델 | `Payment`, `Subscription` | `AppPayment`, `AppSubscription` |
| 라우터 | `/payments/*` | `/billing/*` |
| 서비스 | `payment_service` | `billing_gateway_service` 등 |
| DB 스키마 | `payments`, `subscriptions` 테이블 | `app_payments`, `app_subscriptions` 테이블 |

**이유**: 흐름 A 는 "기록 도구", 흐름 B 는 "결제 중개자". 법적 책임 / 회계 / 운영이 완전히 다르므로 코드 베이스에서 섞이면 안 된다.
