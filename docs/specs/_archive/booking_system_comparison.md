## 2. 경쟁 앱 핵심 기능 분석

### 2.1 캐치테이블 (레스토랑 예약)

**핵심 UX 패턴:**

```
┌─────────────────────────────────────────────┐
│ 예약 플로우                                 │
├─────────────────────────────────────────────┤
│ 1. 검색/탐색 → 레스토랑 선택                │
│ 2. 날짜/시간 선택 (실시간 가용성 표시)      │
│ 3. 예약금 결제 (선결제 → 노쇼 방지)         │
│ 4. 예약 확정 → SMS/푸시 알림                │
│ 5. 방문 전 리마인더 (D-1, 당일)             │
│ 6. 방문 후 리뷰 요청                        │
└─────────────────────────────────────────────┘
```

**배울 점:**

| 기능 | 상세 | 레슨앱 적용 |
|------|------|------------|
| 예약금 시스템 | 노쇼 방지, 취소 수수료 | 체험레슨 예약금 (선택적) |
| 웨이팅 시스템 | 만석 시 대기 신청 | 인기 선생님 대기 명단 |
| 리마인더 자동화 | D-1, D-day 알림 | 레슨 리마인더 (이미 구현) |
| 통합 플랫폼 | 검색→예약→결제 원스톱 | 선생님 검색→체험→정규 플로우 |

## 3. 현재 레슨앱 예약 시스템 분석

### 3.1 현재 아키텍처

```
┌─────────────────────────────────────────────┐
│ 예약 플로우 (현재)                          │
├─────────────────────────────────────────────┤
│                                             │
│ [신규 학생 플로우]                          │
│ 선생님 검색 → 프로필 확인 → 체험레슨 예약   │
│     ↓                                       │
│ 체험레슨 완료 → 수강권 제안 → 결제          │
│     ↓                                       │
│ 수강권 발급 → 정규 스케줄 선택              │
│                                             │
│ [정규 학생 플로우]                          │
│ 정규 스케줄 자동 생성 → 변경/취소 요청      │
│                                             │
└─────────────────────────────────────────────┘
```

### 3.2 강점

| 항목 | 설명 |
|------|------|
| 통합 플로우 | 체험→정규 자연스러운 전환 |
| 수강권 시스템 | 횟수/기간 기반 관리 |
| 3단계 예약 | 선생님 제안→학생 선택→확정 |
| 자동 리마인더 | 레슨 전 알림 (구현 완료) |

### 3.3 개선 기회

| 영역 | 현재 | 개선 방향 |
|------|------|----------|
| 가용성 표시 | 선생님이 3개 시간 제안 | **실시간 가용 슬롯 표시** |
| 노쇼 관리 | 정책만 존재 | **체험레슨 예약금 (선택적)** |
| 그룹레슨 | 미지원 | **정원 관리 + 대기 기능** |
| 선생님 검색 | 기본 필터 | **리뷰 기반 정렬, 상세 필터** |
| 일정 변경 | 선생님 승인 필요 | **셀프 변경 (제한적)** |

## 4. UX/도메인 전문가 관점 개선 제안

### 4.1 UX 전문가 관점

#### 4.1.1 예약 마찰 감소

**문제점:**
- 현재 3단계 예약 (선생님 제안→학생 선택→선생님 확정)은 시간 소요
- 양측 모두 알림 확인 및 응답 필요

**개선안: 선착순 슬롯 예약 (하이브리드)**

```
┌─────────────────────────────────────────────┐
│ 예약 방식 선택 (선생님 설정)                │
├─────────────────────────────────────────────┤
│                                             │
│ ○ 제안 방식 (기존)                          │
│   - 선생님이 3개 시간 제안                  │
│   - 학생 선택 후 확정                       │
│   - 유연한 조정 가능                        │
│                                             │
│ ● 선착순 방식 (신규)                        │
│   - 선생님이 가용 시간 등록                 │
│   - 학생이 직접 예약 (즉시 확정)            │
│   - 예약 충돌 없음                          │
│                                             │
└─────────────────────────────────────────────┘
```

**구현 우선순위: 중간** (선생님 설정 + 학생 예약 UI 필요)

#### 4.1.2 가용성 시각화

**현재:** 텍스트 기반 시간 나열
**개선:** 캘린더 기반 시각화

## 5. 상세 설계

### 5.1 실시간 가용 슬롯 표시 시스템

> ✅ **현재 구현 완료** - 캘린더 + 칩 선택 방식 채택
> 참고: [teacher_availability_spec.md](../schedule/teacher_availability_spec.md)

#### 5.1.1 개요

학생이 예약 시 **주간 캘린더에서 가용 날짜 선택** → **해당 날짜의 가용 시간만 칩으로 표시**

```
┌─────────────────────────────────────────────────────────────┐
│                 현재 방식 (UX 최적화 완료)                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1단계: 캘린더에서 날짜 선택                                  │
│         - 가용 슬롯 있는 날짜에 초록색 점(●) 표시             │
│         - 불가능한 날짜는 흐리게 표시                         │
│                                                             │
│  2단계: 선택한 날짜의 가용 시간만 칩으로 표시                  │
│         - 평소 레슨 시간에 ⭐ 추천 표시                       │
│         - 원클릭으로 시간 선택                               │
│                                                             │
│  3단계: 예약 확정 (즉시)                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**장점:**
- 불필요한 정보 제거 (예약 불가 시간은 아예 표시 안 함)
- 직관적인 2단계 플로우 (날짜 → 시간)
- 기존 학생 홈의 주간 캘린더와 동일한 UI 패턴

**핵심 UX 원칙:**
| 원칙 | 설명 |
|------|------|
| **가용 시간만 표시** | 예약 불가 시간은 아예 노출 안 함 |

| **평소 시간 추천** | 최근 레슨 기록 기반 ⭐ 표시 |

### 5.3 변경권 시스템

> 스튜디오메이트 취소/변경 정책 참고

#### 5.3.1 개요

수강권에 **변경권 횟수**를 포함하여, 학생이 레슨 일정을 변경할 때마다 차감하는 방식

```
┌─────────────────────────────────────────────────────────────┐
│                      변경권 시스템 개요                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [수강권 발급 시]                                            │
│  선생님이 총 레슨 횟수 + 변경권 횟수 설정                     │
│                                                             │
│  예시: 8회 수강권 + 변경권 2회                               │
│                                                             │
│  [학생 레슨 변경 시]                                         │
│  변경권 1회 차감 → 새 시간으로 변경                          │
│                                                             │
│  [변경권 0회일 때]                                           │
│  변경 불가 → 선생님께 직접 문의                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 5.3.7 데이터 모델 변경

```dart
/// 수강권 템플릿 (선생님 설정)
class SubscriptionTemplate {
  final String id;
  final String teacherId;
  final String name;                  // "바이올린 8회 수강권"
  final int totalLessons;             // 8회
  final int validityMonths;           // 3개월
  final int amount;                   // 380,000원

  // 🆕 변경권
  final int rescheduleAllowance;      // 변경권 횟수 (기본 2회)

  // ...
}

/// 수강권 (학생에게 발급)
class Subscription {
  final String id;
  final String studentId;
  final String templateId;

  final int totalLessons;             // 총 레슨 횟수 (8)
  final int usedLessons;              // 사용한 레슨 (3)

  // 🆕 변경권
  final int totalRescheduleAllowance; // 총 변경권 (2)
  final int usedRescheduleCount;      // 사용한 변경권 (1)

  /// 남은 변경권
  int get remainingReschedule => totalRescheduleAllowance - usedRescheduleCount;

  /// 변경 가능 여부
  bool get canReschedule => remainingReschedule > 0;

  // ...
}
```

#### 5.3.8 변경권 사용 규칙

| 상황 | 변경권 차감 | 비고 |
|------|:----------:|------|
| 학생이 직접 변경 | ✅ 1회 | 정상 차감 |
| 학생이 직접 취소 | ✅ 1회 | 취소도 변경권 사용 |
| 선생님이 변경 | ❌ | 학생 변경권 미차감 |
| 선생님이 취소 | ❌ | 학생 페널티 없음 |
| 선생님이 추가 부여 | - | 총 변경권 증가 |

#### 5.3.9 UI 상태별 정리

| 변경권 상태 | 표시 | 버튼 상태 | 추가 안내 |
|------------|------|:--------:|----------|
| ≥ 2회 | "🔄 변경: N/M회" | 활성 | - |
| = 1회 | "⚠️ 변경: 1/M회 (마지막!)" | 활성 | 확인 다이얼로그 |
| = 0회 | "🚫 변경 불가 (0/M회)" | 비활성 | "선생님께 문의" 버튼 표시 |

## 7. 결론

### 7.1 핵심 차별화 요소 (유지)

1. **통합 플로우**: 체험→정규→연습 관리 원스톱
2. **3자 소통**: 선생님-학생-학부모 연결
3. **연습 관리**: 레퍼토리 템플릿, 녹음, 메트로놈

### 7.2 즉시 개선 필요 항목

1. **가용성 시각화**: 캘린더 기반 슬롯 표시
2. **수강권 UI**: 잔여 횟수, 변경 횟수 명확히 표시
3. **리마인더 강화**: 레슨 전/후 자동 알림 (구현 완료)

### 7.3 중장기 검토 항목

1. **선착순 예약 옵션**: 예약 마찰 감소
2. **그룹레슨**: 앙상블, 마스터클래스 지원
