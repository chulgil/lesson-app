# 통합 레슨 신청 플로우 스펙

> **문서 버전**: 2.0
> **최종 수정**: 2026-03-28
> **상태**: v2.0 재설계 — 3타입 통합 + 3안 제시 + 네이버 예약 벤치마크
> **역할**: 학생-선생님 최초 연결부터 레슨 시작까지의 전체 플로우
> **이전 버전**: v1.0 (2026-03-26) — 2타입, 1안 제출, 3라운드 협상

---

## 1. 배경 및 문제 정의

### 1.1 현재 문제 (v1.0에서 발견)

- 희망 레슨 **일자**가 없음 — 요일+시간만 수집, 구체적 날짜 없음
- 학생이 **1안만 제출** → 선생님과 평균 2.3회 메시지 교환 필요 (추정)
- **회차권** 타입이 없음 — 체험/정규 2개만 존재
- 재수강 시 선생님 스케줄 정보가 표시되지 않음
- **3라운드 협상**이 과도하게 복잡 — 메신저보다 불편해지는 역설
- 신청 완료 후 안내가 없음 — 학생이 "다음에 뭘 해야 하지?" 상태
- 악기 1개인 선생님도 악기 선택 UI 노출

### 1.2 v2.0 설계 원칙

1. **메신저/구두 대화보다 편해야 한다** — 이보다 복잡하면 안 됨
2. **학생 3안 제출 → 선생님 1택 → 끝** — 90% 케이스에서 1라운드 확정
3. **네이버 예약 벤치마크** — 주간 캘린더, 안내 메시지, 스텝 가이드
4. **3타입 통합** — 체험/정규/회차권이 하나의 폼에서 UI 전환

### 1.3 참고 서비스 벤치마크

| 서비스 | 참고 포인트 |
|--------|------------|
| 네이버 예약 (미용실) | 주간 캘린더 + 이전/다음 + 예약 안내 메시지 + 스텝 가이드 |
| 숨고 | 선생님 프로필 + 가격 투명성 |
| 클래스101 | 레슨 타입 분류 + 신청 플로우 단순화 |
| 에어비앤비 | 달력 기반 예약 + 확정 프로세스 시각화 |

## 2. 용어 정의

| 용어 | 설명 |
|------|------|
| 레슨 신청 | 학생이 선생님에게 레슨을 요청하는 행위 (체험/정규/회차권 모두 포함) |
| 3안 제시 | 학생이 최대 3개의 희망 시간을 우선순위와 함께 제출하는 것 |
| 주간 캘린더 | 이전/다음 버튼으로 주 단위 탐색 가능한 스케줄 선택 UI |
| 시간 협상 | 학생-선생님 간 레슨 시간을 합의하는 과정 (최대 2라운드) |
| 안내 메시지 | 선생님이 커스텀 가능한 레슨 신청 안내 문구 |
| 가격표 | 선생님이 악기별 x 레벨별로 설정한 레슨 가격 매트릭스 |

## 3. 레슨 타입 정의

| 타입 | 설명 | 일정 성격 | 날짜 선택 UI |
|------|------|----------|-------------|
| **체험레슨** | 첫 만남, 레벨 확인용 1회 레슨 | 특정 날짜 + 시간 | 주간 캘린더 (이전/다음) |
| **정규레슨** | 매주 고정 요일/시간 반복 레슨 | 요일 + 시간 (시작일은 선생님 결정) | 주간 캘린더 → 자동 "매주 X요일" |
| **회차권** | 선생님 일정에 맞춰 매번 예약 | 특정 날짜 + 시간 (매 회차) | 주간 캘린더 (체험과 동일) |

### 4.3 타입별 캘린더 동작 차이

#### 체험레슨 / 회차권 (동일)
- 주간 캘린더에서 **특정 날짜+시간** 선택
- 이전/다음으로 주 이동 (최대 4주 앞까지)
- 과거 날짜 비활성
- 클릭 순환: 1 → 2 → 3 → 초기화(1) → 2 → 3
- 같은 요일+시간 조합 중복 불가
- 선택 리스트에 **"3/26(수) 10:00"** 형식으로 표시

#### 정규레슨
- 주간 캘린더에서 날짜 선택 시 → **"매주 X요일 Y시"** 자동 생성
- 시작 주 정보는 UI에 표시되나 선생님에게는 **요일+시간만 전달**
- 시작일은 선생님이 수강권 발급 시 결정
- 선택 리스트에 **"매주 수요일 10:00"** 형식으로 표시
- 클릭 순환 동일 (최대 3개 요일+시간 조합)

### 4.4 3안 선택 인터랙션 상세

```
슬롯 상태:
  [✓] = 선생님 가용 (선택 가능)
  [×] = 선생님 부재/예약됨 (선택 불가, 회색)
  [·] = 운영시간 외 (표시 안 함)
  [❶] = 학생 1순위 선택
  [❷] = 학생 2순위 선택
  [❸] = 학생 3순위 선택

클릭 순환:
  첫 클릭 → ❶ (1순위)
  두번째 다른 슬롯 클릭 → ❷ (2순위)
  세번째 다른 슬롯 클릭 → ❸ (3순위)
  네번째 다른 슬롯 클릭 → 기존 전부 초기화 → ❶ (다시 1순위부터)

  같은 슬롯 재클릭 → 해당 슬롯만 해제 (번호 재정렬)

제약:
  - 같은 요일+시간 조합 중복 불가
  - 서로 다른 주의 같은 요일+시간도 정규에서는 중복 (체험/회차는 날짜가 다르면 허용)
  - 최소 1개 선택 필수 (3개 모두 선택 권장)
```

## 5. 재수강 (복귀 학생) 처리

### 5.1 진입

`TeacherDetailScreen`에서 [다시 시작하기] → 동일한 `UnifiedLessonRequestScreen`

### 5.2 프리필 규칙

| 필드 | 프리필 값 | 조건 |
|------|----------|------|
| 레슨 유형 | 정규레슨 (변경 가능) | 항상 |
| 악기 | 이전 레슨 악기 | 항상 |
| 캘린더 선택 | 이전 고정일자 자동 선택 | 해당 슬롯이 가용한 경우만 |
| 캘린더 미선택 | "이전 시간(화 14시)은 현재 불가합니다" 안내 | 해당 슬롯이 부재/예약됨 |

### 5.3 LessonRequest 시스템 폐기

기존 `LessonRequest` (재수강 전용 간단 시스템)은 `UnifiedLessonRequest`로 통합 폐기.
- `LessonRequest` 엔티티/레포지토리/프로바이더: deprecated 처리 후 삭제
- `preferredTiming` (다음주/다음달/상담후) 드롭다운: 캘린더로 대체

## 6. 시간 협상 프로세스 (최대 2라운드)

> v1.0의 3라운드에서 2라운드로 축소. 학생 3안이면 대부분 1라운드에서 끝남.

```
Round 1:
  학생 → 희망 시간 최대 3안 + 메모 전송
  선생님 →
    ├── 3안 중 1개 수락 → 시간 확정 ✅ (90% 케이스)
    ├── 3안 모두 불가 + 역제안 최대 3안 + 메모
    └── 거절 → 종료

Round 2 (마지막):
  학생 →
    ├── 역제안 중 1개 선택 → 시간 확정 ✅
    └── 취소 → 종료

  (학생의 재역제안 없음 — 2라운드로 끝내기 위해)

2라운드 미합의 → "시간 협의가 어렵습니다. 메시지로 상담해주세요."
```

### 6.1 선생님 역제안 UI

- 선생님 화면의 주간 스케줄과 동일한 UI (이전/다음, 주간 캘린더)
- 빈 슬롯 클릭 → 대안 시간 추가 (최대 3개, 동일 클릭 순환)
- 메모란 포함

## 9. 네이버 예약 벤치마크 적용 항목

| 네이버 요소 | 적용 | 위치 |
|------------|------|------|
| ✅ 주간 캘린더 + 이전/다음 | 희망 레슨 시간 섹션 | 폼 중앙 |
| ✅ 시술 안내 → 선생님 안내 메시지 | 커스텀 가능 문구 | 폼 상단 (레슨유형 위) |
| ✅ 예약 완료 + 스텝 가이드 | 5단계 수직 리스트 | 완료 페이지 |
| ✅ 예상 소요시간 | 레슨 시간 (60분) 표시 | 폼 내 읽기 전용 |
| ✅ 취소/변경 정책 안내 | "24시간 전 변경 가능" | 폼 하단 (메모 위) |
| ✅ 최근 예약 이력 | 재수강 시 이전 정보 프리필 | 캘린더 자동 선택 |

## 10. 데이터 모델 (v2.0)

### 10.1 UnifiedLessonRequest

```dart
class UnifiedLessonRequest {
  final String id;
  final String studentId;
  final String teacherId;

  // 레슨 정보
  final LessonRequestType type;        // trial, regular, perSession ← NEW
  final String instrument;
  final UnifiedLessonGoal goal;
  final UnifiedExperienceLevel experience;
  final String? message;

  // 희망 시간 — 최대 3안 ← v2.0 핵심 변경
  final List<PreferredTimeSlot> preferredSlots;  // 1~3개
  final int preferredDuration;                   // 60분 기본

  // 시간 협상 (최대 2라운드) ← 3→2 축소
  final List<TimeProposal> proposals;
  final int currentRound;                        // 1-2

  // 재수강 정보
  final bool isReturningStudent;

  // 상태
  final UnifiedRequestStatus status;
  final DateTime createdAt;
  final DateTime? confirmedAt;
  final String? rejectionReason;

  // 가격 참고
  final int? suggestedPrice;
}
```

## 코드 반영 추가 (2026-06-03)

> §10 데이터 모델(v2.0)은 설계 시점 기준이며, 실제 구현 enum 값이 일부 달라졌다. 아래는 현행 코드 기준 정정/추가 사항이다.
> 코드 위치: `features/schedule/domain/entities/unified_lesson_request.dart`

### A. LessonRequestType — 값명 정정

§10.3은 `perSession`으로 표기했으나, **실제 코드는 `package`**를 사용한다.

```dart
enum LessonRequestType { trial, regular, package }  // perSession (X) → package
```

### B. UnifiedRequestStatus — 코드 기준 13개 값

§10.5 대비 실제 enum 차이: `approved` 추가, `negotiating`/`subscriptionIssued`/`inProgress` 존재. `proposalAccepted` 다음 단계로 `paymentNotified`까지는 동일.

```dart
enum UnifiedRequestStatus {
  pending,            // 선생님 확인 대기
  approved,           // 선생님 승인 (코드 전용 — 스펙 §10.5 미기재)
  negotiating,        // 시간 협상 중
  timeConfirmed,      // 시간 확정
  proposalSent,       // 수강권 제안 발송됨
  proposalAccepted,   // 수강권 수락됨
  paymentNotified,    // 학생/학부모가 입금 완료 알림
  subscriptionIssued, // 입금 확인 후 수강권 발급 (Phase 2)
  inProgress,         // 레슨 진행 중 (Phase 3)
  completed,          // 전체 완료
  rejected,           // 거절됨
  cancelled,          // 취소됨
  expired,            // 만료
}
```

상태 분류 헬퍼:
- `isActive` — pending/approved/negotiating/timeConfirmed/proposalSent/proposalAccepted/paymentNotified/subscriptionIssued/inProgress
- `isTerminal` — completed/rejected/cancelled/expired

### C. RequestPhase — 신규 enum (스펙 미기재)

챕터 기반 UI를 위한 라이프사이클 단계 enum. `UnifiedRequestStatus`를 3단계 + 종료 단계로 묶는다.

```dart
enum RequestPhase {
  request,       // Phase 1: 레슨 신청 → 입금
  subscription,  // Phase 2: 수강권 발행
  lessons,       // Phase 3: 레슨 진행
  completed,     // 전체 완료
  terminal,      // 거절/취소/만료
}
```

### D. ProposalAction — 값 추가

§10.4는 `propose, accept, reject` 3개로 정의했으나, 코드는 **`counterPropose`(역제안)** 가 추가된 4개 값이다.

```dart
enum ProposalAction { propose, accept, reject, counterPropose }
```
