## 1. 영상 핵심 요약

### 1.1 AI 생산성 역설

SK아카데미 배수정 RF가 제시한 핵심 공식:

> **팀 성과 = 잠재 성과 - 프로세스 손실**

AI가 개인 생산성을 높여도, 팀 내 속도 차이·소통 단절·학습 증발 등 **프로세스 손실**이 더 커져 팀 전체 성과는 오히려 떨어진다.

### 1.2 4대 프로세스 손실

| # | 손실 | 설명 |
|---|------|------|
| 1 | **저자의 실종** | AI 산출물에 대해 "왜 이렇게 했는지" 설명할 수 없음. 피드백 대상이 사라짐 |
| 2 | **학습의 증발** | 비효율(삽질)을 제거하면서 성장 기회도 함께 제거. 주니어가 깊은 전문성을 쌓지 못함 |
| 3 | **대화의 소멸** | 각자 AI에게 물어보고 끝. 팀원 간 고유 경험·판단이 공유되지 않음. Anthropic 연구 인용: AI 도입 후 사회적 역학이 가장 크게 감소 |
| 4 | **팀의 분열** | 속도 격차 → 불신. AI 능숙자는 3일 만에 끝내고 놀고, 나머지는 1개월. "이 팀이 왜 필요하지?" |

### 1.3 멀티 에이전트 시스템 데모

배수정 RF가 **리더십 진단 시스템**을 혼자 구축한 사례:

**기존 방식**: People Analyst, HR, 데이터 엔지니어, UI/UX, 프론트/백엔드 개발자, PM — 10~15명, 3~6개월

**에이전트 방식**: Claude Code 기반 멀티 에이전트 팀 구성

```
메인 팀                        벤치마킹 팀
├── PM 에이전트                 ├── 문헌 조사 에이전트
├── 백엔드 개발 에이전트         ├── 역사 가이드 에이전트
├── 프론트엔드 개발 에이전트     ├── UI/UX 전문가 에이전트
├── AI 분석 에이전트             └── 데이터 시나리오 에이전트
└── QA 에이전트
```

**도구 선택**:
- **Claude Code**: 멀티 에이전트 오케스트레이션 (메인)
- **Anti Gravity (Gemini)**: 디자인 개선
- **ChatGPT Codex**: 복잡한 디버깅

**참고**: MIT의 "My AI Advisory Board" — 스티브 잡스, 일론 머스크 등 13명의 AI 에이전트가 토론하며 CEO에게 조언하는 모델

## 2. Lessonaza 적용 분석

### 2.1 우리의 상황

| 항목 | 영상 사례 (SK) | Lessonaza |
|------|:-------------:|:---------:|
| 팀 규모 | 10~15명 → 1명+AI | **1명 + AI** |
| 프로세스 손실 | 매우 심각 (4대 손실) | **거의 없음** (솔로 개발) |
| AI 숙련도 격차 | 팀 내 극심 | **해당 없음** |
| 에이전트 활용 | 실험 단계 | **이미 부분 활용** |

**핵심 차이**: 솔로 개발자는 영상에서 말하는 "팀 프로세스 손실"이 **구조적으로 발생하지 않는다**. 오히려 에이전트 팀을 100% 활용할 수 있는 최적의 위치에 있다.

단, 영상에서 경고하는 **개인 수준 문제**는 주의 필요:
- **학습의 증발**: AI가 만든 코드를 이해하지 못한 채 넘어가면 기술 부채가 됨
- **저자의 실종**: 코드 리뷰 없이 AI 산출물을 그대로 커밋하면 품질 저하
- **검증 피로**: AI가 90%까지 빠르게 만들지만 나머지 10% 검증에 큰 노력 필요

### 2.2 현재 에이전트 활용 현황

이미 `~/.claude/agents/`에 11개 에이전트가 구성되어 있음:

| 에이전트 | 역할 | 활용도 |
|----------|------|:------:|
| planner | 구현 계획 | 높음 |
| architect | 시스템 설계 | 중간 |
| tdd-guide | 테스트 주도 개발 | 낮음 |
| code-reviewer | 코드 리뷰 | 높음 |
| security-reviewer | 보안 분석 | 낮음 |
| build-error-resolver | 빌드 에러 수정 | 중간 |
| e2e-runner | E2E 테스트 | 낮음 |
| refactor-cleaner | 데드 코드 정리 | 중간 |
| doc-updater | 문서 업데이트 | 중간 |
| database-reviewer | DB 리뷰 | 낮음 |
| verify-agent | 검증 | 높음 |

**문제점**: 에이전트는 있지만 **팀으로 오케스트레이션**되지 않고, 개별적으로만 사용 중

## 3. 제안: Lessonaza 에이전트 팀 구조

### 3.1 영상 모델 → Lessonaza 적용

배수정 RF의 "메인 팀 + 벤치마킹 팀" 구조를 Lessonaza에 맞게 재설계:

```
┌──────────────────────────────────────────────────────────┐
│                    오케스트레이터 (사용자)                   │
│              작업 정의 → 팀 선택 → 결과 검증                 │
└────────────────────┬─────────────────────────────────────┘
                     │
        ┌────────────┼────────────────┐
        ▼            ▼                ▼
   ┌─────────┐  ┌─────────┐    ┌──────────┐
   │ 설계 팀  │  │ 구현 팀  │    │ 품질 팀   │
   └────┬────┘  └────┬────┘    └─────┬────┘
        │            │               │
   ┌────┴────┐  ┌────┴────┐    ┌────┴─────┐
   │planner  │  │ 코더    │    │code-     │
   │architect│  │(Claude) │    │reviewer  │
   │ux-expert│  │tdd-guide│    │security  │
   └─────────┘  │doc-     │    │verify    │
                │updater  │    │e2e       │
                └─────────┘    └──────────┘
```

### 3.2 작업 유형별 팀 편성

#### A. 새 기능 개발 (예: AI 레슨 노트, 학습 자료 공유)

```
Phase 1: 설계                          Phase 2: 구현                    Phase 3: 검증
┌──────────────────┐                   ┌──────────────────┐           ┌──────────────────┐
│ [병렬 실행]       │                   │ [순차 실행]       │           │ [병렬 실행]       │
│                  │                   │                  │           │                  │
│ Agent 1: planner │                   │ Agent: 코더      │           │ Agent 1: reviewer │
│  → 구현 계획     │                   │  → 코드 작성     │           │  → 코드 품질     │
│                  │──→ 사용자 승인 ──→│  → 테스트 작성   │──→        │                  │
│ Agent 2: UX분석  │                   │  → 문서 업데이트  │           │ Agent 2: verify  │
│  → 경쟁사 조사   │                   │                  │           │  → 빌드/분석     │
│  → UI 설계      │                   │                  │           │                  │
└──────────────────┘                   └──────────────────┘           │ Agent 3: security│
                                                                     │  → 보안 검토     │
                                                                     └──────────────────┘
```

#### B. 리팩토링 (예: 800줄+ 파일 분할)

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ Agent: architect │──→  │ Agent: refactor  │──→  │ Agent: verify   │
│  → 분할 전략     │     │  → 코드 분리     │     │  → 빌드 확인    │
│  → 의존성 분석   │     │  → import 수정   │     │  → 회귀 테스트  │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

#### C. 버그 수정

```
┌─────────────────┐     ┌─────────────────┐
│ Agent: 탐색      │──→  │ Agent: verify   │
│  → 원인 분석     │     │  → 수정 검증    │
│  → 수정 구현     │     │  → 빌드 확인    │
│  → 테스트 추가   │     │                 │
└─────────────────┘     └─────────────────┘
```

### 3.3 신규 에이전트 제안

현재 부족한 역할:

| 에이전트 | 역할 | 필요 이유 |
|----------|------|----------|
| **ux-researcher** | 유사 서비스 분석, UX 패턴 조사 | 이번 학습 자료 스펙 작성 시 수동으로 진행했던 작업 자동화 |
| **spec-writer** | 스펙 문서 초안 작성 | 사용자 요구 → 유사 서비스 분석 → 스펙 초안까지 자동화 |
| **mock-data-generator** | Mock 데이터 생성/검증 | 방금 수동으로 했던 Mock 데이터 수정 9건 같은 작업 |
| **integration-tester** | 크로스 모듈 통합 검증 | 모듈 간 데이터 일관성 (membership ↔ subscription 등) |

## 4. 구체적 워크플로우 제안

### 4.1 `/auto` 강화: 계획→구현→검증 자동 파이프라인

현재 `/auto` 스킬을 영상의 멀티 에이전트 패턴으로 강화:

```
사용자: "학습 자료 공유 Phase 1 구현해줘"

1단계: planner + ux-researcher (병렬)
  ├── planner: 구현 계획 + 파일 목록 + 의존성
  └── ux-researcher: 유사 서비스 UX 패턴 최종 확인

2단계: 사용자 승인 (HARD-GATE)
  └── "이 계획으로 진행할까요?"

3단계: 구현 (순차, worktree 격리)
  ├── 엔티티/모델 생성
  ├── Provider 구현
  ├── UI 위젯 구현
  ├── Mock 데이터 생성
  └── 스펙 문서 업데이트

4단계: 검증 (병렬)
  ├── code-reviewer: 코드 품질
  ├── verify-agent: flutter analyze + 빌드
  └── security-reviewer: 보안 체크

5단계: 결과 보고
  └── "구현 완료. 리뷰 이슈 0건, 빌드 성공, 보안 이슈 없음."
```

### 4.2 "AI 자문단" 패턴 (MIT 모델 적용)

영상에서 언급된 MIT "My AI Advisory Board"를 스펙 설계에 적용:

```
사용자: "AI 레슨 노트 기능을 어떻게 설계할지 다각도 분석해줘"

Agent 1 (음악 교육 전문가 관점):
  "레슨 중 녹음은 학생 긴장을 유발할 수 있습니다.
   녹음 시작 시 학생에게도 안내가 필요합니다."

Agent 2 (UX 디자이너 관점):
  "녹음 인디케이터는 최소화해야 합니다.
   레슨 집중을 방해하지 않는 subtle한 표시가 좋습니다."

Agent 3 (백엔드 엔지니어 관점):
  "60분 오디오 업로드는 청크 분할이 필수입니다.
   Whisper API는 25MB 제한이 있어 분할 전송 필요합니다."

Agent 4 (개인정보 법률 전문가 관점):
  "한국 개인정보보호법상 음성 녹음은 정보주체 동의 필수.
   녹음 사실을 학생/학부모에게 고지해야 합니다."

→ 종합 → 스펙에 반영
```

### 4.3 "저자의 실종" 방지 전략

영상의 경고를 Lessonaza 개발에 적용:

| 위험 | 방지 전략 | 구현 |
|------|----------|------|
| AI 코드를 이해 못한 채 커밋 | code-reviewer가 "왜 이렇게 구현했는지" 질문 포함 | 리뷰 에이전트 프롬프트에 "설계 의도 설명 요청" 추가 |
| 스펙과 코드 불일치 | verify-agent가 스펙 대비 구현 검증 | SDD 리뷰 강제 규칙 (이미 있음) |
| 학습 없이 복붙 | TDD 강제 (테스트 먼저 작성) | tdd-guide 활용도 높이기 |
| 검증 피로 | 검증 자동화 (병렬 에이전트) | verify-loop 스킬 활용 |

## 6. 핵심 교훈

### 영상에서 가져갈 것

1. **멀티 에이전트 = 가상 팀**: 혼자 개발해도 PM/개발자/QA/UX 역할을 에이전트로 분리하면 품질이 올라간다
2. **벤치마킹 팀 패턴**: 구현 전에 별도 에이전트 그룹이 조사/분석을 완료하면 구현 방향이 명확해진다
3. **QA 에이전트 필수**: 구현 에이전트와 검증 에이전트를 **반드시 분리**해야 한다 (자기 코드를 자기가 검증하면 안 됨)
4. **도구 조합**: Claude Code(오케스트레이션) + 다른 AI(특수 작업)의 조합이 효과적

### 영상에서 주의할 것

1. **학습의 증발 경계**: AI가 만든 코드도 반드시 이해하고 넘어가기. 특히 아키텍처 결정
2. **저자 의식 유지**: "이 코드의 설계 의도를 내가 설명할 수 있는가?" 자가 점검
3. **검증 피로 관리**: 자동 검증 파이프라인을 구축하여 수동 검증 부담 최소화
