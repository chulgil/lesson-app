# Frontend Verify — Playwright 스크린샷 기반 회귀 검증

> autopus `auto verify` 패턴 흡수 (2026-04-23).
> 목적: UI 변경이 의도한 화면만 바꿨는지, 다른 화면을 깨뜨리지 않았는지를 **시각적으로** 확인. 타입체크/단위테스트는 "코드가 컴파일됨" 만 보장한다.
> 보완: 플러그인 `ux-consistency-check` 스킬과 병행 (스킬은 플러그인 업데이트 시 덮어씀, 이 규칙은 프로젝트/글로벌 영속).

## 적용 범위

프론트엔드 변경이 포함된 커밋:
- `frontend/lib/**/*.dart`
- `web/src/**/*.{ts,tsx,vue,svelte}`
- 스타일 파일 (`.css`, `.scss`, theme 토큰)
- 라우터/레이아웃 파일

백엔드만 변경, 데이터 마이그레이션, 문서 변경 → 이 규칙 비적용.

## UX/i18n 일관성 계약

프론트엔드 변경 전후에 같은 도메인 흐름이 여러 화면에 걸쳐 있는지 먼저 검색한다.
예: 목록, 상세, 하단 액션 바, 바텀시트, 알림, 말풍선, 히스토리 카드.

동일 흐름에는 같은 단계명과 CTA 언어를 사용한다.
- 단계명: 요청 → 선택/제안 → 확정/거절/대기처럼 사용자가 이해하는 업무 단계 기준
- CTA: 같은 결과를 만드는 버튼은 화면마다 다른 표현을 쓰지 않는다
- 상태 배지: 목록과 상세의 상태명은 같은 의미 체계를 공유한다
- 이벤트 기록: 확정/거절/제안 이벤트는 사용자가 입력한 메시지와 선택 데이터를 함께 표시한다

사용자-facing 텍스트는 하드코딩하지 않는다.
- Flutter: `AppStrings` 또는 프로젝트 l10n 계층 사용
- Web: i18n/messages/constants 계층 사용
- 테스트 문자열도 가능하면 같은 public 문구를 검증하되, 새 문구는 먼저 공통 문자열 계층에 추가한다

새로운 UI 문구나 CTA 를 추가할 때는 다음을 확인한다.
1. 같은 기능을 쓰는 화면을 `rg` 로 찾는다
2. 기존 공식 용어가 `.harness/knowledge/glossary.md` 또는 문자열 계층에 있는지 확인한다
3. 목록/상세/바텀시트/알림/말풍선의 단계명과 CTA 를 맞춘다
4. 입력 메시지가 히스토리 또는 말풍선에 표시되는지 회귀 테스트를 추가한다
5. 하드코딩 텍스트 검색 결과가 남지 않는지 확인한다

## 검증 흐름

### autopus 사용 시

```bash
# 변경된 프론트엔드 파일 자동 감지 → Playwright 스크린샷 생성 → diff 리포트
auto verify

# 자동 수정 없이 리포트만
auto verify --report-only

# 모바일 뷰포트로 검증
auto verify --viewport mobile
```

기본값: `--fix true` — 쉬운 CSS 회귀(여백, 색상)는 자동 수정 시도 후 스크린샷 재촬영.

### autopus 미사용 환경

수동 3단 검증:

1. **변경 경로 확인**: `git diff --name-only` 에서 프론트엔드 파일 식별
2. **영향 화면 매핑**: 각 파일 → 어느 화면에 사용되는지 수동 조사 (grep 으로 import 체인 추적)
3. **실기 확인**: 개발 서버 띄우고 영향 화면 + 공통 레이아웃 2~3개를 직접 확인

3단계는 CLAUDE.md 상위 지침("UI 변경은 브라우저에서 실기 확인") 과 일치.

### Agentic 검증 루프 (권장 기본 — Dart/Flutter MCP + web + chrome MCP)

> 전략 SSOT: 옵시디언 `10 Projects/레슨앱/40-Flutter-AI-개발속도-전략`. 사람이 매번 chrome 을 수동으로 여는 의식을 에이전트가 스스로 도는 루프로 대체한다.

`.mcp.json` 에 **dart** MCP 서버 등록됨(공식 Dart & Flutter MCP). UI 변경 시 이 루프를 우선 사용:

1. `flutter run -d web-server --dart-define=...` 로 앱 기동 (`-d chrome` 아님 — 그 경우 Flutter 가 띄운 창에만 핫리로드가 가서 에이전트가 모는 브라우저와 어긋남).
2. 코드 편집 후 Dart MCP `hot_reload` → 초 단위 반영.
3. Dart MCP `get_runtime_errors` / `get_widget_tree` 로 런타임 에러·위젯트리를 **에이전트가 직접** 확인(로그 수동 판독 대체).
4. 픽셀 스크린샷은 **chrome-devtools MCP** 로 375 / tall 뷰포트 촬영 — flutter_driver 스크린샷은 web 빌드 미지원이므로 브라우저 MCP 와 페어링.
5. golden test 가 있는 화면은 golden 회귀로 실폰트 오버플로우까지 기계 검출(§아래 "실폰트" 항목).

한계·주의:
- web 빌드에서 flutter_driver 의 탭/입력/스크린샷은 미지원 → 픽셀 검증은 chrome MCP 담당, 상태·에러·핫리로드는 Dart MCP(DTD) 담당으로 역할 분리.
- 모바일 실기 렌더(노치·키보드·시스템바)는 이 루프로 못 잡음 → 그 클래스는 여전히 실기/시뮬레이터. web 루프는 레이아웃·오버플로우·상태 회귀용.
- MCP 등록 변경은 세션 재시작 후 활성.

## 뷰포트 커버리지

한 번의 검증에 최소 2개 뷰포트:
- 기본: `desktop` (1440x900)
- 모바일: `mobile` (375x667) — 반응형 깨짐 자주 발생

tablet 은 태블릿 전용 레이아웃 변경 시에만.

## 리포트 판독

Playwright diff 이미지에서:
- **빨간 박스** = 레이아웃 변형 (의도적 or 회귀)
- **노란 박스** = 색상/타이포그래피 변화
- **파란 박스** = 새로 나타난 요소

모든 박스는 **의도한 변경인지 설명**할 수 있어야 한다. 설명 불가능한 박스 = 회귀.

## 실패 처리

- **의도한 변경인데 스냅샷이 오래됨** → 스냅샷 업데이트 후 재실행
- **의도하지 않은 회귀** → 수정 후 재검증. 스냅샷 업데이트로 은폐 금지.
- **flaky (애니메이션/폰트 로딩)** → wait 조건 추가하거나 해당 영역 마스킹, 스냅샷 자체는 유지.

## 금지

- 스크린샷 테스트 실패 → 실패 이유 확인 없이 스냅샷 재생성 (회귀 은폐)
- 프론트엔드 커밋에 이 규칙 적용 누락 → 단위 테스트만 통과했다고 PR 제출
- 의도한 변경을 모두 "자동 수정" 에 맡기기 → 자동 수정은 단순 회귀만, 의도한 변경은 수동 반영

## 트리거 시점

| 시점 | 실행 |
|---|---|
| 프론트엔드 변경 커밋 전 | `auto verify --report-only` |
| PR 생성 시 | CI 에 `auto verify` 게이트 연결 |
| 디자인 시스템 변경 (theme/tokens) | 전체 앱 스크린샷 재촬영 (범위 넓음, ultra 모드) |
| 레이아웃 리팩토링 | PR 설명에 before/after 이미지 첨부 |
